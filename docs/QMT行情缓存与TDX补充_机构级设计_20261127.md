# QMT 行情缓存 + TDX 补充（Parquet 架构与接线规划）

日期：2026-11-27
范围：Windows 伴生桥（`deploy/qmt-pipe-bridge/`）+ QuantMind 后端行情层
已拍板：**桥侧落盘用 Parquet**；TDX 补充放后端统一合并；其余按推荐默认。
目标：**下单前取价快、行情准、数据全、掉线可续；下游接口不变**。

---

## 0. 结论先行

三层缓存：

1. **内存热层**（桥进程）：全市场最新快照、当天 1m、热集 tick 环；
2. **Parquet 温层**（桥侧磁盘）：按 `date/type/hour` 分区的不可变 part + 原子 manifest，崩溃/掉线可续；
3. **后端统一行情层**：TDX（10 档/L2）为主、QMT 为备，合并/新鲜度/交叉校验，输出到现有 Redis key。

QMT 策略进程**不放缓存**；订单路径**不读不写缓存、不等缓存锁**；现有 RPC/Redis/TDX/前端接口**不改**，只做加法。

---

## 1. 为什么是 Parquet（而不是 SQLite WAL）

- Parquet 是**不可变文件**：写入即 part，原子 rename 提交；崩溃最多丢最后一个未提交 part，不会出现 DB 锁/损坏/半写页。
- 列式压缩（zstd）对行情表非常合适：1m 全市场 125 万行/日、3s 全市场 2,500 万行/日，压缩后 50MB / 0.5–1.5GB 级。
- 后端 DuckDB/Polars 可直接读，不用 ETL；与 QuantDB 分析栈一致。
- 读取按分区/列裁剪，适合「当天某几分钟、某批代码」的查询。
- 代价：Parquet 不支持原地 append，必须写 part；我们用「小 part + manifest」解决。

### 依赖策略（稳定优先）

- 桥侧使用 `pyarrow` 写 Parquet；**只在写入线程内延迟 import**，import 失败不拖垮桥：
  - 正常：`pyarrow` 可用 → 直写 Parquet part；
  - 降级：`pyarrow` 不可用 → 写 gzip JSONL spool（同一套 manifest），桥继续跑，状态标 `degraded`，后端/人工可转 Parquet；
  - 部署前预检：`python -c "import pyarrow; print(pyarrow.__version__)"`。
- 不引入 pandas 作为桥依赖；pyarrow 只用 `Table.from_pylist` / `parquet.write_table`。
- 若后续要彻底隔离 GIL/内存，可把 writer 拆成 sidecar 进程；V1 先线程内、接口按 sidecar 可替换设计。

## 4. Parquet 存储设计

### 4.1 目录

```
qmt-tools/data/cache/qmt/
  date=20261127/
    type=bar1m/hour=09/part-000001.parquet
    type=bar1m/hour=10/part-000002.parquet
    type=snapshot3s/hour=09/part-000001.parquet
    type=tick_hot/hour=09/part-000001.parquet
    manifest.json
```

- `part` 命名：`part-<seq>.parquet`，seq 单调递增；
- `manifest.json`：版本、创建时间、每个 part 的 `{type,hour,file,rows,min_ts,max_ts,sha256,created_at}`；
- 不按 symbol 分区：全市场一次写入行数大、按时间分区更均衡；查询用谓词下推 + 内存索引。

### 4.2 写入协议（崩溃一致）

1. 写线程从有界队列取批（按 5 秒或 5 万行切）；
2. 写临时文件 `<part>.tmp`，`flush + os.fsync`；
3. `os.replace(tmp, part)` 原子提交；
4. 计算 sha256，原子更新 `manifest.json`（`manifest.json.tmp` → replace）；
5. 只有 manifest 中的 part 被视为有效；`.tmp`/孤儿 part 启动时忽略并清理。

崩溃最多丢「已写 tmp 未提交」的一批；已提交 part 不会半写。

### 4.3 Schema

**bar1m**

| 列 | 类型 | 说明 |
|---|---|---|
| date | string | YYYYMMDD |
| symbol | string | 后缀式，如 600036.SH |
| minute_ts | int64 | 分钟起点 epoch ms |
| open/high/low/close | float64 | 1m OHLC |
| volume/amount | float64 | 累计/增量按上游口径统一为增量 |
| vwap | float64 | amount/volume |
| source | string | qmt / tdx |
| final | bool | 最后一根是否收盘 |

**snapshot3s**

| 列 | 类型 |
|---|---|
| date, ts_ms, symbol | string/int64/string |
| last, open, high, low, pre_close, volume, amount | float64 |
| bid1..bid5, ask1..ask5, bid_vol1, ask_vol1 | float64 |
| source, quality | string |

**tick_hot**

| 列 | 类型 |
|---|---|
| date, ts_ms, symbol | string/int64/string |
| last, volume, amount, bid1, ask1 | float64 |
| source | string |

- 主键逻辑：`(date, symbol, ts)`；写入前去重；`INSERT OR REPLACE` 语义用「后写覆盖」实现。
- 统一后缀式代码；Redis/前端前缀式由现有工具转换。
- 时间：Asia/Shanghai；`ts_ms` 为 epoch ms；`date` 用交易日。

### 4.4 读取

- 内存优先：latest / 1m / hot tick；
- 未命中：manifest 找 part → `pyarrow.parquet.read_table(filters=[...])` → 内存 LRU；
- 1m 查询按 `(symbol, minute_ts)` 谓词；3s 按 `(symbol, ts_ms)`；
- 大范围查询（全市场 1m）走内存数组，避免读盘。

### 4.5 保留与压缩

- `bar1m` 30 天、`snapshot3s` 5 天、`tick_hot` 10 天（可配）；按 date 目录清理；
- zstd 压缩；row group 128MB 以内；每天可选 compact（合并小 part）——V3 再做，先保证写入简单。

## 5. 内存设计（速度优先）

| 结构 | 内容 | 估算 |
|---|---|---|
| `LatestSnapshot` | 5,225 只最新 tick（规范化 dict） | ~1–3MB |
| `Bar1mStore` | 每只 240×8 个 float，`array('d')` 扁平存储 | ~80–120MB |
| `HotTickRing` | 持仓+热集+指数，最近 N 分钟，deque | 20–50MB |
| `Snapshot3sRing` | 最近 60–120 档全市场（可选，V3） | 30–80MB |

- 读路径无锁：写线程构建新对象后**整体替换引用**（copy-on-write）；
- 写路径只锁聚合器最小临界区；绝不与 `rpc_worker` 的订单分支共享锁；
- 超内存阈值：降级只保留 latest + 1m，关闭 3s 环并告警。

## 6. 接线（pipe_redis_bridge.py 只做薄接线）

### 6.1 初始化

```python
# 顶部（try/except 保护，缓存失败不影响桥启动）
try:
    from qmt_today_cache.service import TodayCacheService
    TODAY_CACHE = TodayCacheService.from_config(CFG, BASE)
except Exception as exc:
    TODAY_CACHE = None
    log('today_cache disabled: %r' % (exc,))
```

### 6.2 数据入口

| 入口 | 调用 | 说明 |
|---|---|---|
| `sweep_worker` | `TODAY_CACHE.ingest_ticks(ticks, source='qmt')` | 全市场 5 分钟一轮，补 1m 聚合 |
| 新 `snapshot_worker` | 每 `today_cache.snapshot_interval_s`（默认 3s）`get_full_tick(universe)` → ingest | 1m 聚合主来源；V3 同时写 snapshot3s |
| `quotes_worker` | 热集 ticks → `ingest_hot_ticks` | V2 热集 tick |
| `rpc_worker` 的 `get_full_tick` 响应 | `ingest_ticks`（可选，去重） | 用户请求也能喂缓存 |

- 所有 ingest 都是**非阻塞入队**；队列满丢最旧并记 `cache_dropped`；
- 缓存异常一律 `try/except` + 指标，绝不向行情/订单路径抛。

### 6.3 查询拦截

| 方法 | 行为 |
|---|---|
| `get_full_tick` | 请求的**全部**代码都在内存且新鲜（≤ `max_age_s`）→ 直接返回同形状 dict；否则原样转发 QMT。不返回半份缓存，避免语义变化 |
| `get_market_data_ex` | **不改**：QMT 返回格式是 code_map(DataFrame)，桥内无 pandas，直接透传 |
| `cache_today_1m`（新增） | 列式返回 `{symbol: {minute_ts:[...], open:[...], ...}}` 纯 JSON；单次上限 600 只；后端 `qmt_today_cache_client` 消费 |
| `cache_status`（新增） | 命中率、队列、内存、磁盘、last_flush、degraded |

- 新增方法只做加法；现有方法签名/返回不变。
- `get_full_tick` 命中时构造 `resp` 走现有 `write_reply`，`request_id` 用当前请求的 id。

### 6.4 后端接线

- `qmt_today_cache_client.py`：`client('rpc').call('cache_today_1m', {...})`；超时 2s；失败回落 QMT/QuantDB。
- `unified_quote_cache.py`：
  - 读 TDX `market:snapshot:tdx:{symbol}`（或现有 canonical，按阶段）；
  - 读 QMT canonical/`cache_today_1m`；
  - 合并后写回现有 `market:snapshot:{symbol}`（key 不变，追加 `source/quality/as_of`）；
  - 交叉校验：价差 >1% 或时间差 >5s → `divergent` + 告警。
- `quote_cache_reader.py`：保留现有签名；内部优先 canonical；未命中回落 QMT，行为不变。

## 7. TDX 行情补充

| 项 | 设计 |
|---|---|
| 定位 | TDX 主（10 档/L2/逐笔），QMT 备（全市场 L1），QuantDB 历史 |
| 合并 | 新鲜度 → 完整度 → 源优先级；同一返回体不混源 |
| 键 | 现有 `market:snapshot` 不变；新增 `market:snapshot:tdx/qmt/merged` 作为内部来源（V3） |
| 冲突 | 价差 >1% 或时间差 >5s 标 `divergent`，交易决策用 TDX，告警 |
| 缺口 | TDX 无该标的/停牌无推送 → QMT；QMT 无 → `missing`，不猜 |
| 下单前 | 读 canonical snapshot（TDX）→ 陈旧读 QMT 内存/`cache_today_1m` → 都无再走 QMT 管道；订单元数据记 `quote_source/quote_ts` |

桥侧不直连 TDX 8550（避免重复消费）；如未来要桥独立顶替，再启 `today_cache.tdx_supplement=true`。

## 8. 稳定性与防护（机构级）

- **隔离**：缓存服务独立线程；`rpc_worker` 订单分支零锁；缓存失败熔断（连续 N 次禁用，后台恢复）。
- **有界**：ingest 队列、part 大小、内存、磁盘配额；超限丢最旧 + 指标 + 告警。
- **磁盘**：剩余 <5GB 停写；按日保留；写失败重试有限次，转 `degraded`。
- **原子**：tmp → replace；manifest 原子更新；sha256；启动校验；损坏 part 隔离不加载。
- **时间**：统一 Asia/Shanghai；09:00 新日、15:05 finalize；时钟偏差 >2s 告警。
- **数据质量**：每条带 `source/as_of/final/quality`；不伪造；`gap` 显式。
- **开关**：`today_cache.enabled=false` 全透传；`degraded` 只 spool 不写 Parquet。
- **安全**：symbol/日期正则校验；不拼接任意路径；缓存目录权限最小化；查询只读；无订单方法。
- **维护**：manifest/schema 带 version；模块边界清晰；sidecar 可替换；测试覆盖崩溃/降级/跨日。

## 9. 性能预算（验收）

| 场景 | 目标 |
|---|---|
| 单标的取价（内存/Redis） | p95 < 20ms |
| 全市场 `get_full_tick` 缓存直出 | p95 < 150ms（含序列化） |
| 热集 600 只当天 1m 全量（列式） | p95 < 300ms |
| 热集 tick（≤600 只） | p95 < 30ms |
| 订单路径延迟 | 变化 ≤5%（A/B 开关对照） |
| 1m 写入 | <5% CPU；part 5 分钟一批 |
| snapshot3s 写入 | <50MB/s；日增 <1.5GB |
| 崩溃恢复 | 1m <10s；3s <30s；已提交 part 不丢 |
| 内存 | <300MB（不含 3s 环） |

**Kill criteria**：订单延迟 +10% / 缓存锁阻塞订单 / ingest 延迟 >50ms / 内存 >500MB / 日增 >2GB / 已提交 part 丢失 / 错误价格未标 divergent → 立即回滚（关开关/还原 `.bak`）。

### 代码审计（本轮已修）

1. `LatestSnapshot` 多线程 copy-on-write 可能丢 symbol → 锁内 copy+swap；
2. `parse_range_ms` 起止同一天时 end 被当成 00:00 → end 取当日 23:59:59.999；
3. 盘中重启首 tick 会把全天累计量算进第一根 bar → `_first_start`（开盘 ≤09:30 从 0；盘中从当前累计；恢复用最后 bar 累计）；
4. 同分钟迟到 tick 会覆盖 close/高低点 → `ts < state._last_ts` 丢弃；
5. 旧 tick 阈值 6h 太宽 → 10 分钟（冷门股不再造 bar）；
6. Parquet flush 跨日/跨小时写进同一 part → 按 `(date,hour)` 分组；
7. manifest `file` 可路径穿越 → 读取时校验必须位于 `date=` 目录；
8. 全市场 1m 查询构造 list-of-dicts 持锁 1.1s → 列式 `query_columns` + 锁内仅 array 切片；600 只全量 **1.118s → 0.063s**；
9. pyarrow 缺失时 status 未标降级 → `degraded=True` + `format=jsonl.gz`；
10. 新增 `query_max_symbols=600` 上限，超限显式错误，避免大 JSON 拖垮桥；
11. 服务跨日切换加 `_rollover_lock`，避免两个 ingest 线程同时 reset；
12. `PartStore.flush` 自动建目录；status 用 `started` 与 service `enabled` 区分。

### 待真机验证 / 已知边界

- Windows 桥进程真机启动、pyarrow 预检（未装则 `degraded=1`，JSONL spool 可跑）；
- 硬 kill 只丢当前未完成分钟；已提交 part 不丢；

## 18. 桥稳定启动器（2026-11-27 真机）

### 问题

- 旧 `start_pipe_bridge.cmd` 是裸 python 启动：重复执行靠进程自身单实例锁；旧进程残留时只会静默退出/抢文件，不会清理；
- 从 SSH 用 `Start-Process` 拉起的进程会随会话断开被杀（本次部署实测）；
- 看门狗与人工启动可能并发。

### 方案

- `start_pipe_bridge.ps1`：
  - `Global\QMTToolsPipeBridgeLauncher` 互斥锁；
  - 目标只来自 PID 文件、17719/17720 端口 owner、命令行含 `pipe_redis_bridge`；
  - 端口被非桥进程占用 → 拒绝启动（不误杀 TQ/文件桥）；
  - 杀完等待端口释放，清理失效 PID 文件；
  - `Win32_Process.Create` 分离启动，等待 17720 监听，失败返回非 0；
  - 日志 `logs/start_pipe_bridge.log`。
- `start_pipe_bridge.cmd` 包装器 → ps1；`start_pipe_bridge_raw.cmd` 保留裸命令；
- `pipe_watchdog.ps1` 改为调用 ps1；
- 计划任务 `QMTTools-StartPipeBridge`（SYSTEM/Highest/IgnoreNew），`register_start_pipe_bridge.ps1` 可重建。
- **一键启动**：`bridge-windows\启动交易台.cmd`（ASCII 别名 `start_trading_desk.cmd`）= 现有 TDX 交易台 launcher + QMT `start_pipe_bridge.ps1`；QMT 健康时 `NOOP`，`-Restart` 才 `-Force`；`-NoPause -NoUi` 供自动化。
- **启动质检**：一键启动最后调用 `qmt-tools\cache_quality_check.py`（`-NoCacheCheck` 可跳过）：
  - 配置：account/Redis、rpc 间隔/突发/读超时、budget 队列、risk 金额/频率/偏离、quotes/sweep/cache/snap3s/source_http 开关、pyarrow 版本；
  - 运行时：strategy_state、pos/asset age、queue；
  - 缓存：enabled/degraded/errors/dropped/latest/last_ingest/hot/snap3s/parts；
  - 数据：Parquet 最新 part 列/行/样例价格；盘中 TDX/QMT 来源键采样价差（>1% 告警）；
  - 退出码 0/2/1（OK/WARN/FAIL），一键启动打印 `CACHE rc`。
- 安全默认：`start_pipe_bridge.ps1` 在 17720 已监听且 `bridge_health.py` 返回 0/3/4 时直接 `NOOP`；只有缺失/不健康或 `-Force` 才清理重启，避免盘中误重启。
