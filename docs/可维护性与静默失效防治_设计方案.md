# 可维护性与静默失效防治_设计方案（AI 协作友好）

> 版本：v1（2026-09-15）　配套：`docs/统一交易栈_设计方案.md`（v3）、`docs/设计复盘与优化报告.md`
> 动机（用户明确）：**"改 bug 都要搞很多 token 出去"**——本项目由 AI 协作开发，可维护性的核心度量就是：**定位与修复一个缺陷，平均需要读多少文件/token**。
> 本次实测基线：一次"模拟盘不对劲"的诊断读了 **100+ 文件**。目标：同类问题降一个数量级。

---

## 一、度量与目标

| 指标 | 基线（本次实测） | 目标 |
|---|---|---|
| 定位一个缺陷读的文件数 | ~100 | ≤ 10 |
| 诊断脚本覆盖的常见故障 | 0 | top-20 症状 → 一键命令 |
| 回归防护 | 未知 bug 靠人肉记忆 | 每个历史 bug 一条测试 |
| 新人/AI 上手（首次改动核心模块） | 需全库摸索 | 读 1 页代码地图即可下手 |

## 二、代码地图（`docs/CODEMAPS/`）

**每模块一页**，同构模板（AI 会话先读地图 → 直击目标，不再全库逛）：

```markdown
# CODEMAP: simulation（模拟盘）
- 职责：一句话
- 入口文件：engine.py / scheduler.py / routers/simulation.py（各一句话）
- 对外契约：Signal / Order / Ledger 的哪个部分、在哪实现
- 依赖：Redis(db2 账户键) / PG(sim_* 表) / QuantDB（行情）
- 关键数据流：信号→调仓→撮合→账本→快照（一图）
- 常见故障：症状→根因→文件（top-5，链 Runbook）
- 禁区：不许绕过 OrderRouter 下单 / 不许手写账户键
```

v1 覆盖四个核心模块：`simulation`、`inference`（信号）、`live_trading`（执行/镜像）、`strategy`（策略/存储）。后续按改动热度补。

## 三、Runbook（`docs/RUNBOOK.md`：症状 → 一键命令 → 根因）

| 症状 | 一键命令 | 常见根因（链 CODEMAP） |
|---|---|---|
| 模拟盘没成交 | `python scripts/diagnose/sim.py --user X` | 信号未就绪/账户键不一致/风控拦截/行情缺失 |
| 资金曲线不对 | 同上（含曲线-快照一致性检查） | 用户 ID 口径/跨市场合并/基线膨胀 |
| 今日无信号 | `python scripts/diagnose/signal.py --date X` | 推理未跑/残 run/就绪标记缺失/闸门异常 |
| 下单被拒 | `python scripts/diagnose/order.py --order-id X` | 风控规则/资金/涨跌停/通道 |
| 策略改不动/删不掉 | `python scripts/diagnose/strategy.py --id X` | 状态机/校验/异步调用缺陷 |
| …（从本次诊断 12 例 + 历史故障补到 20 条） | | |

原则：**症状进、报告出**——脚本输出"红黄绿 + 具体文件行号 + 建议动作"，人与 AI 都不再手工翻库。

## 四、一键体检（`scripts/diagnose/health.py`）

每日自动 + 手动可跑，12 项断言（与交易台"系统健康卡"同源）：

1. 信号分布正常（非全 HOLD、非分布坍缩）｜2. 就绪标记与残 run 检查｜3. 账户键一致性（同用户多键检测）｜4. 曲线 ↔ 快照 ↔ 账户 数字同源｜5. PG 台账有写入（成交必落账）｜6. 对账差异为零或已解释｜7. 调度任务心跳齐｜8. 配置生效回读（策略参数/风控参数/REDIS 配置）｜9. 数据同步完整（五市场）｜10. 模型契约一致（hash/lag/池）｜11. 风控状态正常（非 HALT 滞留）｜12. 执行链路连通（模拟+实盘预检）

输出：交易台健康卡 + 每日报告（异常自动推送）。

## 五、静默失效防治（专项，来自 12 个真实 bug 的 8 类静默模式）

| 防治手段 | 说明 |
|---|---|
| **fail-loud 清单** | 关键路径（信号生成/下单/落账/快照/调度/对账）异常必须告警；禁止 debug 级吞掉、禁止静默跳过（清单落到代码注释与评审项） |
| **每日体检断言集** | §四（把"没人发现"变成"当天告警"） |
| **配置生效检查** | 参数保存后自动回读验证（对治 min_score/execution_config/live_config 类死配置） |
| **一致性对账扩展** | Redis↔PG↔券商、模拟↔影子、曲线↔快照→订单——数字对不上自动报告（已有雏形，补齐覆盖面） |
| **契约校验强制** | Model Contract / Signal 就绪 / Order 幂等——三处强校验已经是"拒绝运行"而非"警告" |
| **WARNING 点名制** | 关键闸门全零时打 WARNING 点名被哪道挡住（已有 signal_side 先例，推广） |

## 七、错误自定位规范（错误信息 = 半个修复）

关键路径错误信息统一格式：

```
[CONTRACT:MODEL] lang mismatch: label.lag=1 vs backtest.lag=0 (model=mdl_xxx, strategy=stg_yyy) → check model_contract.py:check_lag
[RULE:RL1-04] reject buy 600036.SH: single position 18% > limit 15% (run_id=..., rule_version=v12) → risk/rules/position.py
```

三段式：`契约/规则 ID + 具体数值对比 + 文件:函数`。日志直接指路，不用搜。

## 九、备份与灾难恢复（DR，终审补充缺口）

| 对象 | 策略 | 频率 | 恢复目标 |
|---|---|---|---|
| PG（账本/订单/评分/审计） | 全量 + WAL 归档 | 每日全量 + 持续 WAL | RPO ≤ 5min，RTO ≤ 1h |
| Redis（热状态/账户缓存） | 可重建（PG 权威）→ 不需要独立备份，但保留 AOF | — | 重建脚本一键（按市场重建） |
| QuantDB/量化数据 | 已有数据目录 + 快照 | 随同步 | 可从源重灌 |
| L2 原始层 | 落地即备份（冷层归档） | 每日 | 可重解析 |
| 密钥/配置 | Secret 管理 + 配置版本库 | 变更即存 | — |
| **演练** | 每半年一次"从备份恢复全链路"演练 | — | 报告归档 |

**验收**：Disaster Recovery 演练走通一次（模拟"PG 损坏 → 恢复 → 对账 → 交易恢复"）。

## 十、权限与角色（RBAC，终审补充缺口）

| 角色 | 可读 | 可写 | 备注 |
|---|---|---|---|
| 消费者用户 | 自己的全部数据 | 自己的策略/设置/模拟盘 | 默认角色 |
| 运营/客服 | 用户数据（只读）+ 诊断报告 | 推送/公告 | 无资金/风控写权 |
| 策略审核（未来多角色） | 全部 | 策略晋级审批 | — |
| 管理员 | 全部 | 风控参数/系统配置（**双人复核**）/ kill switch | 关键操作留痕 |
| AI/Agent | 按工具白名单 | **默认只读**；写操作需人工审批 | 六铁律之一 |

原则：**最小权限 + 关键操作双人 + 全量审计**；消费者永远碰不到风控参数与系统配置。
