# QMT 桥稳定性加固（机构级细案）

日期：2026-11-27
范围：Windows 伴生桥（`deploy/qmt-pipe-bridge/`）+ QuantMind 客户端轮询（`backend/services/live_trading/`）
目标：**交易链路绝不被行情/账户查询拖垮**；「QMT 在线·账户滞后」从反复发生降为可观测、可自愈、可人工接管的事件。

---

## 2. 失败模式与加固点

| # | 失败模式 | 现有护栏 | 本次加固 |
|---|---|---|---|
| F1 | 主线程变慢 → 固定速率继续打 → 完全挂死 | 固定令牌桶（3s/2s） | **自适应 Governor**：EWMA 延迟 >1.2s 即把交易查询间隔翻倍（封顶 8×），连续 3 次健康才逐级减半 |
| F2 | 多个消费者重复查同一事实（容器轮询、桥内 positions/orders、账户同步、健康探针） | 各自限速，仍重复 | **交易只读短缓存**（资产/持仓 2s、委托/成交 1s），订单/撤单后立即失效 |
| F3 | 看门狗重启风暴：`bridge_restart_ts` 无限增长、每分钟重启 | 小时预算 6 次、固定 60s 冷却 | **指数退避**（60s→120s→…→30min）+ **30 分钟 ≥4 次判风暴停止自动重启** + 时间戳裁剪（50 条/24h） |
| F4 | QMT 非当前交易券商时仍每 5s 打 `query_orders` | 无 | **活跃券商门控**：非 `qmt_exec` 且无未平 QMT 单 → 空转 60s；有遗留未平单 → 低频对账 |
| F5 | 桥不健康时固定 5s 硬打 | 仅记日志 | **客户端指数退避** 5s→10s→…→120s，成功一轮清零 |
| F6 | 账户同步在陈旧/空账户时仍 30s 打 | 固定 30s | 陈旧 → 120s、空账户 → 60s、失败指数退避至 300s |
| F7 | 看门狗/重启风暴无人看见 | 只有管道指标告警 | **`qmt_pipe_guard` 读 `qm:qmt:strategy:watchdog`**：主线程卡死 >180s、重启风暴、Tap 未装配均告警到管理员/QQ |
| F8 | QMT 全推未装配（`quote_push_ready=0`/Tap disabled） | 无 | **默认不告警**（行情主源 TDX，QMT 全推只是备源；需告警时 `QM_QMT_ALERT_TAP_DISABLED=true`）；QMT 状态仍可在 `/api/v1/qmt/health` 查看 |

## 3. Kill criteria（验收失败即回滚）

- **K1**：模拟主线程 3s 延迟时，桥在 60s 内把交易查询有效速率降到 ≤1/2，且不提前判 `unresponsive`。
- **K2**：同一 `method+params` 在 TTL 内重复请求，主线程调用次数 = 1；缓存命中不消耗令牌、不改写 `request_id`。
- **K3**：30 分钟内第 4 次自动重启必须被阻止，状态为 `alert` 且原因含 `storm`；`bridge_restart_ts` 永远 ≤50 条。
- **K4**：QMT 非活跃券商且无未平 QMT 单时，`QmtExecPoller` 交易查询数 = 0；有未平单时仍能在 60s 内对账。
- **K5**：`qmt_pipe_guard` 在策略看门狗 `account_ok=0` 持续 180s 后产生一次告警；恢复后产生一次恢复通知。
- **K6**：订单/撤单路径语义不变（永远不被限速、不被缓存、不被风暴护栏丢弃）；TDX 交易链路无任何行为变化。

## 4. 代码改动

### 4.1 新增 `deploy/qmt-pipe-bridge/bridge_stability.py`（纯函数，Linux 可单测）

- `GovernorState` / `observe()` / `effective_interval()`：自适应交易查询调速。
- `TradeReadCache`：线程安全的交易只读短缓存（key 归一、TTL、invalidate、命中统计）。
- `RestartConfig` / `restart_decision()` / `cap_stamps()` / `append_stamp()`：重启风暴、指数退避、时间戳裁剪。
- 单测：`deploy/qmt-pipe-bridge/tests/test_bridge_stability.py`（16 例）。

### 4.2 `pipe_redis_bridge.py`

- `rpc()` 记录交易上下文方法的成功/失败延迟 → Governor；
- `rpc_worker` / `market_call` 的交易查询间隔改走 `trade_interval()`；
- `rpc_worker` 转发前查 `TRADE_CACHE`，成功且 `ok=True` 才写缓存；命中时重写 `request_id`；
- 交易只读查询超时缩短为 `rpc.trade_read_timeout_s`（默认 8s）：单线程 worker 等一条挂死查询时，后面的订单也在排队；
- 任何订单/撤单方法进入前 `TRADE_CACHE.invalidate()`；
- `_metrics_snapshot` 新增 `governor_multiplier / governor_ewma_ms / trade_cache_hits/misses/entries`；
- 新配置项见 `bridge_config.example.json`（有默认值，旧配置无需改也能跑）。

### 4.3 `qmt_strategy_watchdog.py`

- `should_restart_bridge` 改为返回 `(allowed, reason, storm)`；
- 重启前用 `stability.restart_decision()` 判定风暴/小时预算/指数退避；
- `evaluate` 写侧裁剪 `bridge_restart_ts`；
- 风暴时返回 `alert`（不再 fallback 到 `reload`），文案要求人工在 QMT 编辑器停止→运行策略。

### 4.4 客户端（backend）

- `qmt_exec_poller.py`：
  - `poll_decision()` / `next_backoff_s()` 纯函数；
  - 活跃券商门控（`active_broker_type()`）+ 未平 QMT 单检查（DB，7 天窗口，读失败 fail-safe 继续对账）；
  - 失败指数退避（`STRATEGY_UNHEALTHY/BRIDGE_BUSY/RPC_ERROR/TIMEOUT`；THROTTLED 单独计数）；
  - 新指标 `gate_skips / backoff_skips`。
- `qmt_account_sync_task.py`：陈旧/空账户/失败分级退避。
- `qmt_pipe_guard.py`：`evaluate_strategy_watchdog()` 纯函数 + 任务循环读取 `qm:qmt:strategy:watchdog`，把「主线程卡死 / 重启风暴」并入现有边沿告警；**推送按相关性门控**（`_qmt_alerts_relevant`：QMT 是当前券商或有未平 QMT 单才推送），Tap 未装配默认不告警（`QM_QMT_ALERT_TAP_DISABLED=true` 可开），避免 QMT 作为备源时 7×24 噪音。

### 4.5 测试

- `deploy/qmt-pipe-bridge/tests/test_bridge_stability.py`（16 例）。
- `backend/tests/test_qmt_exec_poller.py` 新增 7 例（退避/门控/遗留单/限速分账/告警相关性）。
- `backend/tests/test_qmt_pipe_guard.py` 新增 5 例（看门狗状态解析）。
- `deploy/qmt-pipe-bridge/tests/test_qmt_strategy_watchdog.py` 更新为 3 元组 + 风暴/裁剪用例。

本地验证（2026-11-27 容器内，pytest 不可用时用等价 runner 执行纯函数用例）：
`bridge_stability` 16/16、`qmt_strategy_watchdog` 35/35、`qmt_pipe_guard` 26/26、
`qmt_exec_poller` 32/32 全过（仅 caplog/tmp_path/parametrize 类用例跳过）。
容器内 `py_compile` 三个后端模块通过；真实环境烟测 `active_broker=tdx`、
`has_open_qmt_orders=False`，重启后轮询门控将直接空转。

## 6. 观察指标（上线后 1 周）

- `bridge_restart_ts` 每小时新增次数（目标：0；>2 需复盘）
- `governor_multiplier` 分布（目标：多数时间 1.0；持续 >2 说明 QMT 主线程长期偏慢）
- `trade_cache_hits / (hits+misses)`（目标：>40%）
- `QmtExecPoller.gate_skips`（非 QMT 券商时应持续增长，且 `errors` 不再快速增长）
- `[QmtSync] 陈旧快照` 次数/日（目标：0）
- `qmt_pipe_guard` 告警次数（主线程卡死 / 重启风暴；仅在 QMT 为当前券商或有未平 QMT 单时推送）

## 7. 明确不做 / 后续

- 不把订单/撤单纳入限速或缓存（订单路径语义不变）。
- 不让 QMT 承担全市场行情主源：行情以 TDX 为主，QMT 仅备源；QMT 全市场一次拉取实测 11.5s，足够做备用，但不作为常态负载。
- 不在盘中重启交易服务或修改 Windows 桥配置；所有上线动作收盘后执行。
- **后续（未在本批）**：`rpc_worker` 是单线程 FIFO，一条挂死的交易只读查询仍会让后面的订单最多排队 `trade_read_timeout_s`（已压到 8s）。彻底的订单插队需要把 Redis 队列改成「订单优先」的原子 Lua 取件（扫描/移动/LREM 一步完成），涉及队列语义，需单独评审与演练，不在本批强行上。
