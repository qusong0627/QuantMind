## 二、根因（四条，均已修复或收口）

1. **错误策略入口**：10:08 重启后跑的是旧入口 `BIGQMT_REDIS_DRYRUN.py`，不含行情 Tap
   （桥日志持续 `quote_tap_subscribe: rpc method is not allowed`）。行情回退到
   「250 只每 2s 轮询 + 全市场扫」，把单线程管道打满。
   → 正确入口 `C:\xmt\python\QMT_BRIDGE_V2.py`（账户 40327478、transport=pipe、
   `_tap_install` 装 Tap）。

2. **配对调用被饿死**：QMT 交易查询呈「用几次就楔死」——连续 2 次成功（304ms/146ms）
   后第 3 次 15s 超时；楔死后空载 7 分钟不自愈。positions worker 每轮连发
   `get_asset`+`get_positions`，第二轮起必然凑不齐，`pos_age` 一路涨到 4028s。
   → positions 改单发、asset 降频缓存。

3. **止损假成功**：派发层对任何幂等命中一律回 `success`，不管旧单是不是 rejected。
   执行器据此记「已提交」，`failed: 0`。
   → 幂等命中的成败改由旧单终态决定；执行器对 `duplicate_terminal` 直接终态告警。

4. **积压回灌**：楔死期间容器轮询继续入队，桥每 15s 才放掉一条；重启 QMT 后积压
   立刻灌进新策略（三次重启存活 12h → 6min → 3min）。
   → 熔断：账户通道判死后交易类只读请求本地快速失败，不再转发/回灌。

## 四、遗留问题（未闭环）

1. **QMT 交易查询楔死的根因在 QMT 内部**（`get_trade_detail_data` 累积性阻塞）。
   我们做的是降频 + 自愈，不是根治。楔死时账户数据最多滞后 60-90 秒。
2. **容器 11:30 的优雅重启触发者未查明**；存量 docker 日志仅保留约 90 分钟，
   现场已被轮转掉。
   - **受控实验（13:42，盘中经授权）**：`kill -TERM <trade 子进程>` → main_oss
     20 秒内重生新子进程（新 PID，8002 health=200），**容器未重启**（其余子进程
     uptime 不变）。结论：11:30 的整机重启不是「kill 子进程」触发的，外部触发源
     仍未定位。
   - 待办：配置日志保留（json-file max-size/max-file 或落盘）；加容器重启记录器。
3. **规则表被覆盖的风险**：本次 8 条人工规则从配置消失，写了审计但未定位到写入者。
   审计要等 trade 服务下次重启才加载。
