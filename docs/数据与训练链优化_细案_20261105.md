# 数据与训练链优化细案（P1 → P2，基于 next）

> 日期：2026-11-05 · 分支：`next` · 范围：P1、P2 十一项；P0（训练池 SQL 下推、rank_ic 节流）不在本细案内，作为可并行的独立小改动。
> 纪律：先规划后实施；每项先补测试再改实现；所有结论以代码/实测为据，未实测项标注「待验证」。

## 0. 目标与边界

**目标**：把 next 的数据链、SDK 接入、模型训练三块从「能跑」推进到「可对账、可复现、可解释」：

1. 数据：同步后能自动发现缺口/截断/漂移；退市股与 PIT 财务不再静默污染训练。
2. SDK：客户端配置统一、流量/失败可观测、版本与列集有契约、下载前有预算闸。
3. 训练：训练/推理特征契约在晋升时 fail-closed；数据集版本化；滚动就绪与训练缓存可复现。

**边界**：
- 不改变现有默认训练源（`l1_factors`）；V5 宽表仍为可选，先 A/B 再定默认。
- 不在本细案内做 P0 两项（池下推、rank_ic 节流）；它们应在 Phase A 之前或并行完成，否则大数据集训练仍会被旧瓶颈拖住。
- 所有新增开关默认「不改变现有行为」；阻断类闸门需显式启用或只在晋升/训练关键路径生效。

## 2. 工作包

### Phase A — P1 数据正确性

#### A1. QuantDB 同步语义质量闸门（WP1）

**目标**：每次同步后自动判断「数据是否完整、是否异常」，异常写入 `data_quality_alerts` 并在数据管理页可见。

**设计**
1. 新增 `backend/services/engine/data_platform/quantdb_quality.py`：
   - `coverage(dataset, root, calendar, lookback_days)`：最近 N 个交易日应到未到的分区、最新日期 lag。
   - `partition_stats(dataset, root)`：最新分区行数/标的数，与近 20 个分区中位数比较（阈值默认 ±50%，可配）。
   - `schema_drift(dataset, root)`：对最新分区取 `ParquetFile.schema_arrow.names` 的 sha256，与 `data/quantdb/.quality/schema/{dataset}.json` 比对。
   - `run_quality_gate(datasets, root, *, lookback_days=10, mode="warn"|"block") -> dict`；告警去重（同一 `dataset+issue+fingerprint` 一天只写一次）。
2. 挂载点：`quantdb_daily_sync.run_daily_sync` 在 `delisted_inject` 之后、PG 回填之前调用；结果写入 `result["quality_gate"]` 和 `data/quantdb/.quality/latest.json`。
3. 严重度：
   - 最新分区缺失 / 行数较中位数跌 >50% → `error`（默认仍不阻断同步，只告警；`QM_QUANTDB_QUALITY_GATE=block` 时阻断 PG/Qlib 阶段）。
   - 历史分区缺口 / 列集漂移 → `warning`。
4. 管理面：`GET /api/v1/admin/data-platform/quantdb/quality`（admin）返回最新报告；前端「数据管理 → QuantDB」加一张质量卡（覆盖/最新日期/异常项/最近告警）。

**改动文件**：新增 `quantdb_quality.py`；`quantdb_daily_sync.py`；`api/routers/admin/quantdb_console.py`；前端 `AdminDataManagement`/`QuantDBCatalogPanel` 附近加卡片。
**测试**：`backend/tests/test_quantdb_quality.py`（合成 parquet：正常/缺分区/行数跌/列漂移/告警去重）；同步钩子用 monkeypatch 验证结果字段。
**验收**：删一个最近分区 → 下一次同步出 error 告警且页面可见；正常同步零误报；`block` 模式下 PG 回填被跳过并给出原因。
**风险/回滚**：闸门只读不写数据；默认 `warn` 不改变同步结果，回滚=删调用点。
**依赖**：无。

#### A2. 退市股因子覆盖（WP2a）

**目标**：让训练池里的退市股在因子库中也有行，消除幸存者偏差；至少覆盖「可由 OHLCV 派生」的因子。

**设计**
1. 复用 `delisted_daily_store` 的独立仓与 manifest；新增 `backend/scripts/delisted_factor_inject.py`：
   - 对 `MATERIALIZED_LIBRARIES`（factor_defs / cand_factors / factor1300 / gap_mined / l1_batch1_factors / rd_mined）逐分区，把退市股 symbol 的「可派生列」补进主分区（只增不改、幂等、原子写 + manifest 记录 added/list + 前后 sha256）。
   - 不可派生列（依赖 L2 逐笔/盘口/外部数据的）留空并在 manifest 标记 `not_derivable`。
   - 上游下载类库（l1_factors/l2_factors/l1_l2_factors/factor_dictionary）不做本地造数，只产出覆盖率报告。
2. 覆盖率报告：`data/quantdb/factor_research/delisted_coverage.json`，按库统计「退市股应有行/实际行/可派生列覆盖率」。
3. 训练侧：`load_data` 的池过滤后检查池内退市标的的因子覆盖率；低于阈值（默认 80%）时 `warning`，`QM_TRAIN_DELISTED_STRICT=1` 时阻断。
4. 先做单库探针（建议 `cand_factors` 或 `factor_defs`），确认派生列与在市股口径一致，再批量。

**改动文件**：新增脚本；`quantdb_daily_sync.py` 加可选钩子（默认关）；`docker/training/data/loading.py` 加覆盖率告警；`factor_materialize/contract.py` 增加 `delisted` 统计。
**测试**：合成 2 只退市股 + 1 个库，验证只增不改/幂等/原子/not_derivable 标记；覆盖率报告数值。
**验收**：探针库退市股覆盖率 ≥80%（可派生列）；重复执行行数不变；上游分区重写后自动补回；含/不含退市股的 OOS IC 对拍报告（不预设谁更优）。
**风险/回滚**：本地回算会引入口径差异；先单库探针 + manifest 可回滚；上游库不造数。
**待拍板**：可派生列清单与阈值（建议先只补 OHLCV 派生的动量/波动/量能类，不碰基本面/微观结构）。

#### A3. PIT 财务审计（WP2b）

**目标**：确认 V5 `fun_*` 财务因子的公告日对齐，给出可解释的污染清单；不达标因子默认不进训练。

**设计**
1. 收编 `financial_pit_panel.py` 为正式脚本（加 `--build`/`--audit`），输出 `5_technical_derived/margin/financial_pit.parquet`（已有）。
2. 审计器 `backend/scripts/audit_factor_pit.py`：
   - 对 V5 中 `fun_*`（以及可映射的财务类）分别用「报告期对齐」与「公告日+1 交易日对齐」计算截面 IC（同一模型/同一窗口），输出每列 ΔIC、样本数、受影响年份。
   - 判定：`|ΔIC| > 阈值(默认 0.01)` 或污染样本占比 > 1% → `pit_pending`。
3. 结果写 `factor_catalog` 的 `pit_status`（新列：`pit_ok` / `pit_pending` / `not_fundamental`）与审计报告；训练默认排除 `pit_pending`（`QM_TRAIN_INCLUDE_PIT_PENDING=1` 可显式包含）。
4. 用已有的 2026-10-22 前视审计作基线（TTM 缺守卫但真污染仅 0.043%），不重复全量重算，只对 V5 新增/未审列做增量。

**改动文件**：`financial_pit_panel.py`（转正）；新增 `audit_factor_pit.py`；`backend/scripts/bootstrap_factor_catalog.py` 或目录 schema 加 `pit_status`；`docker/training/data/loading.py` 的排除逻辑。
**测试**：合成一个报告期/公告日错位的因子，审计器能标 `pit_pending`；正常因子标 `pit_ok`；金样面板的公告日 + T+1 断言。
**验收**：审计报告落盘；训练默认排除 `pit_pending`；审计前后 IC 差异可复算。
**风险**：公告日字段缺失/错填会误判；先做小样本人工核对；`pit_pending` 默认排除，可用开关恢复。
**待拍板**：ΔIC 阈值与「污染样本占比」阈值；建议 0.01 / 1% 起步。

### Phase B — P1 SDK 与契约

#### B1. SDK 客户端统一 + 流量/失败可观测（WP3）

**目标**：所有 QuantDB 调用走同一份超时/重试/Key 读取；每个数据集的下载字节、耗时、失败率可查。

**设计**
1. 新增 `backend/shared/quantdb_client.py`：
   - `get_client(purpose="sync"|"admin"|"adapter")`：动态读 `runtime_secrets.QUANTDB_API_KEY`；`sync` 用 `(15,300)/3`，`admin`/`adapter` 用 `(15,120)/3`；`QUANTDB_API_HOST` 可配。
   - `instrument(client, dataset)` 包装 `download_file` / `load_as_df` / `query_*`：记录 bytes/duration/ok/error。
2. 指标落 Redis：`quantmind:quantdb:usage:{YYYYMMDD}` 为 hash，字段 `{dataset}:bytes`、`{dataset}:files`、`{dataset}:errors`、`{dataset}:seconds`；同时写 `HealthMonitor` 的 `quantdb` 源（已有 key 规范）。
3. 替换：`quantdb_daily_sync._make_client`、`adapters/quantdb_adapter._get_client`、`admin/quantdb_console` 的临时 client。
4. 管理面：`GET /api/v1/admin/data-platform/quantdb/usage-stats?days=7` 返回按数据集/按天的字节与失败率；与 `get_usage()` 的 `used_gb` 做日对账（差异 >5% 告警）。

**改动文件**：新增 client 模块；三处 client 创建点；`quantdb_console.py`；前端数据管理页。
**测试**：`test_quantdb_client.py`（配置注入、Key 轮换、异常记录）；Redis 指标写入/读取；与 `get_usage` 对账的 mock。
**验收**：一次同步后能看到每个数据集下载字节/耗时；模拟 410/超时后错误计数增加；日流量与账户 usage 对账在阈值内。
**风险**：包装层可能改变 SDK 调用签名；先包最小方法集，逐处替换。

#### B2. SDK 版本/列集契约（WP4）

**目标**：SDK 升级或上游列集变化时，升级前就能发现，不把问题留到训练/推理。

**设计**
1. 新增 `backend/shared/quantdb_contract.py`：
   - `EXPECTED_SDK_VERSION = "0.5.0"`（允许 `0.5.x` 补丁）。
   - `FACTOR_DICTIONARY_COLUMNS_SHA`：从 `backend/tests/fixtures/quantdb_factor_dictionary_schema.json`（列名列表）计算 sha256。
   - `check_sdk_version()`：启动时校验，不匹配 `warning`（不阻断启动），管理页显示。
   - `check_factor_dictionary_schema(path)`：对已同步的最新分区比对列集，漂移 → `warning` + `data_quality_alerts`。
2. 金样：`quantdb_factor_dictionary_schema.json` 由一次真实分区生成（只含列名，不含数据）；测试比对当前分区（未同步则 skip）。
3. 与 WP5 联动：训练 metadata 的 `factor_schema_hash` 在晋升时强校验。

**改动文件**：新增 contract 模块 + 金样；`main_oss.py` 启动打点；`quantdb_daily_sync`/`quantdb_console` 调用。
**测试**：版本不匹配/列集增删的契约测试；金样与本地分区比对。
**验收**：换 SDK/列集，测试或启动告警可见；正常环境零噪音。

#### B3. 训练/推理特征契约 + 晋升闸门（WP5）

**目标**：模型晋升前确认「训练时用的特征源、schema、特征列、数据截止日」现在仍然成立；不成立就 fail-closed。

**设计**
1. 新增 `backend/shared/training/contract.py`：
   - `validate_model_contract(model_id) -> ContractReport`：
     - 读 metadata：`factor_source`、`factor_field_sources`、`features`、`factor_schema_hash`、`data_fingerprint`。
     - `QuantDBFactorReader.describe(source)`（`asyncio.to_thread`，60s 缓存）：源可用、列集 hash、特征可得性（含跨库 `库:列`）。
     - 规则：源不可用 → block；schema hash 不匹配 → block（可通过 `allow_schema_drift` + 理由放行，写入 rollout evidence）；特征缺失 → block；`data_fingerprint.labels_max_date` 为空 → warn。
2. 接入两处默认切换：
   - `model_rollout_service.promote`：在事务前调用；block 则 `RolloutInvalid` 并列出原因。
   - `model_registry.set_default_model`：同样调用；block 返回 422。
3. API/前端：晋升弹窗显示 contract 检查结果；`allow_schema_drift` 仅在 admin + 理由时可选。
4. 复用推理侧已有的漂移检查（`inference/data_loader.py:221`），把「只告警」升级为「晋升阻断」，但不改在线推理行为。

**改动文件**：新增 contract 模块；`model_rollout_service.py`；`model_registry.py`；`api/routers/model_rollouts.py`/`model_training.py`；前端晋升对话框。
**测试**：`test_training_model_contract.py`（ok/漂移/缺列/源不可用/带理由放行）；两条晋升路径各一例。
**验收**：构造一个缺列模型，rollout 与直接 set_default 都被拦；正常模型不受影响；绕过路径有审计记录。

### Phase C — P2 工程化

#### C1. 数据集目录单一来源（WP6）

**目标**：新增数据集只改一处；同步清单与目录不再漂移。

**设计**
1. `DatasetSpec` 增加 `sync: Literal["v2","v1","optional_v2","none"]`、`default_sync: bool`。
2. `quantdb_daily_sync.py` 从 `DATASETS` 派生 `V2_DATASETS`/`V1_DATASETS`/`OPTIONAL_V2_DATASETS`（保持 `category_id`/`dir` 同源）。
3. 测试：`test_quantdb_sync_catalog.py` 把派生结果与当前三份硬编码清单做金样比对；新增 `assert_catalog_sync_parity()` 启动/CI 校验。

**验收**：派生清单与现状逐项一致；新增数据集只改 `DATASETS`；`factor_dictionary`/`etf_kline` 仍为 optional。

#### C2. SDK 配额预算闸（WP8）

**目标**：大流量同步（如 32GB V5 宽表）在下载前就知道够不够，不把配额打穿。

**设计**
1. 同步前预检：对选中数据集，V2 用 manifest 的 `size` 汇总新增/变更分区；V1 汇总变更对象；得到估算字节。
2. 读 `get_usage().remaining_gb` 与 `QUANTDB_DAILY_BUDGET_GB`（默认 0=不限制）；超限 → `QuantDBBudgetError`，API 返回 422 + 预估/剩余。
3. 管理台「开始同步」弹窗展示预估；显式 `confirm_budget=...` 才能继续；夜间默认同步先跳过 optional。
4. 同步后回填实际字节（B1 指标），与预估比对，偏差 >30% 记 warning。

**验收**：模拟剩余 1GB、选 V5 → 不下载并给出 422；正常小数据集不受影响；实际/预估偏差可查。

#### C3. 滚动训练就绪纳入分区覆盖（WP10）

**目标**：缺分区的窗口不再进入滚动训练。

**设计**
1. `rolling_dispatch._factor_dates` 之外，调用 A1 的 `coverage(source, window)`；不足 → `ReadinessResult(False, "factor_coverage_gap", detail)`。
2. 只对 `recipe.factor_source` 为 QuantDB 直读源的 recipe 生效；旧 parquet recipe 保持现状。
3. 测试：合成缺一天的分区，dispatch skip 且 reason 可见；完整窗口通过。

**验收**：造缺口 → 明确拒绝；正常窗口不受影响。

### Phase D — P2 效率与可复现

#### D1. V5 宽表按需物化（WP7）

**目标**：训练只读需要的列，避免每次从 571 列/32GB 宽表重复取数。

**设计**
1. 新增 `backend/scripts/materialize_factor_dictionary_narrow.py`：
   - 输入：feature list、日期窗、源分区；用 DuckDB `SELECT symbol, date, <cols>` 读 `factor_dictionary`，写 `6_ml_datasets/factor_dictionary_sel/{set_id}/dt=YYYYMMDD/data.parquet`（原子写 + manifest：源分区指纹、列集 hash、行数）。
   - `set_id = sha256(排序后的 feature list)[:12]`；manifest 记录源 schema hash，源变化即失效重建。
2. 注册：`FactorSource` 增加 `factor_dictionary_sel`（或在 `config/factor_libraries.yaml` 加派生库）；`FACTOR_SOURCE_DIRS`/`MARKET_FACTOR_SOURCES`/金样同步。
3. 训练/推理可把 `factor_source` 指向该派生库；metadata 记录 `derived_from=factor_dictionary` + `set_id`。
4. 是否设为默认：先用 A/B（`l1_l2` vs V5 全宽表 vs V5 窄表）决定，不直接改默认。

**验收**：窄表与宽表选中列逐值一致；重复训练读取耗时下降；A/B 的 OOS IC 不劣于 `l1_l2` 才考虑默认。
**风险**：派生数据不是上游 PIT 原件；manifest 必须完整，禁止覆盖式重建。

#### D2. 训练数据集 generation/active 指针（WP9）

**目标**：训练读到的一定是完整的一代数据，而不是重建中的半成品。

**设计**
1. 对 `MATERIALIZED_LIBRARIES`（自有物化库）引入 `generation.json`：
   ```json
   {"generation_id":"g20261105T0300","created_at":"...","source_fingerprint":"...","partitions":1234,"schema_hash":"...","status":"active"}
   ```
   同级 `active` 文件/指针原子切换（tmp+rename）。
2. 物化编排：先在临时目录/新代次目录写，校验通过后切 active；失败不动指针。
3. 训练配置记录 `factor_generation`；`QuantDBFactorReader` 在请求带 `generation` 时校验存在且 active；不带则维持现状（兼容旧模型）。
4. API：`GET /api/v1/.../generations/active`；前端训练页显示当前代次。

**验收**：重建过程中训练用旧代次；切换后新代次；metadata 记录代次；失败代次不可见。
**风险**：文件系统原子性在 NFS/CIFS 上的边界；本项目数据盘为本地/数据盘，先按原子 rename 设计，CIFS 场景标注待验证。

#### D3. 训练数据缓存（WP11）

**目标**：同源同特征同窗口的重复训练不重复读盘/构标签。

**设计**
1. 缓存键：`sha256(factor_source, source_stamp, train_start, train_end, sorted(features), label_horizon, execution_lag, pool_hash, cache_version, image_git_commit)`。
   - `source_stamp`：源分区文件数 + 最新日期 + schema hash + 最新分区 `size:mtime` 摘要（不做 GB 级内容哈希）。
2. 缓存目录：`QM_TRAIN_CACHE_DIR`（默认 `/workspace/cache/train`）；Parquet/Feather + `meta.json`（键输入、行数、列 hash、生成时间）。
3. `load_data` 命中前校验 `source_stamp` 与键；不一致 miss。写入 tmp + rename；缓存上限（默认 5GB）按 LRU 清理。
4. 默认开启但只缓存「直读因子源 + 明确 feature list」的路径；旧 parquet 路径不缓存，避免行为变化。

**验收**：同参重训命中、帧 hash 一致；数据/特征/代码版本变化必 miss；缓存上限生效。
**风险**：缓存键漏项会导致脏读；键必须包含 schema/source stamp/code version，宁可多 miss。

## 4. Kill criteria（出现以下情况就停/降级）

1. A1 闸门在正常日误报 >1 次/周 → 先修阈值/去重，不上 `block`。
2. A2 单库探针的退市股派生列与在市股口径差异 > 可解释范围 → 只产出覆盖率报告，不写回因子库。
3. A3 审计发现 `pit_pending` 占比 >10% 且集中在核心因子 → 先修 PIT 面板，不接入训练。
4. B3 晋升闸门误拦正常模型 >1 次/周 → 先修缓存/描述接口，不扩大到在线推理。
5. D1 窄表 A/B 的 OOS IC 劣于 `l1_l2` → 保留为可选派生库，不设为默认。
6. D2 在目标数据盘上原子 rename 不可靠 → 降级为「只读 active 指针 + 双缓冲目录」，并标注待验证。
7. D3 缓存命中导致任何一次帧 hash 不一致 → 立即默认关闭缓存，修键。
