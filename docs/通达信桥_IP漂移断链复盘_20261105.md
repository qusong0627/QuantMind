# 通达信桥 IP 漂移断链复盘（2026-11-05）

> 13 号 Windows 机（ESXi `192.168.31.224` 上的 `win10` VM）DHCP 从 `192.168.31.13`
> 漂到 `192.168.31.250` 后，QMT 全链离线。**表层症状全是「超时」，真正原因有两层，
> 第二层会让「改 `.env` / 改容器环境变量 / 重建容器」全部无效。**

## 时间线

| 时间（北京） | 事件 |
|---|---|
| 11-05 14:26 | Windows VM 被硬重启（`cleanShutdown=FALSE`），重启后 DHCP 分到 `.250` |
| 14:26 起 | 平台指向 `.13`，行情与 QMT 全断 |
| 20:00 | 8550 桥可达但 `qmt.online=false`（`TimeoutError`，探 `127.0.0.1:17720`） |
| 20:12 | Redis 转发桥白名单放行 `.250`，QMT 管道恢复（`qmt.online=true`） |
| 20:21 | 修正 Redis 运行时桥配置并重启 `quantmind`，QMT 账户快照恢复落库 |

## 症状（很有迷惑性）

- `GET http://<win>:8550/api/v1/health` → `qmt.online=false`，`error=TimeoutError`
- Windows 侧伴生桥 `127.0.0.1:17720` **在 listen**、`Test-NetConnection` 通，
  但 `GET /health` **20 秒不返回**
- `logs\pipe_bridge.log` 反复出现 `WinError 10053`（客户端先断开，是被超时掐断的假象）
- 伴生桥 `health failed: network:ConnectionError`（每 5s）
- 平台 `[QmtSync] 拉取账户失败 code=BRIDGE_UNREACHABLE: 桥不可达: ConnectTimeout`（每 42s）
- `bigqmt:position_events` 停在 2026-10-30 18:14（该流本身是 25–40 分钟一条，不是 3 秒）

## 根因一：Redis 转发桥的源 IP 白名单

`quantmind-redis-lan-bridge`（`deploy/redis_lan_bridge.py`，`--network host`）
在 `192.168.31.68/.56:6379,6380` 上按 **源 IP 白名单** 转发到 `127.0.0.1:6379`，
原白名单只有 `.13/.68/.56`，`.250` 被拒：

```
[redis-lan-bridge] 拒绝非白名单来源 192.168.31.250 → 192.168.31.68
```

连锁：伴生桥写心跳失败 → `/health` 在持锁时还调 `R.llen()`，连 Redis 卡 20s →
超过 8550 桥探活的 **2s** 超时 → `qmt.online=false`。

**修复**（`.13` 保留，便于回迁）：

```bash
docker rm -f quantmind-redis-lan-bridge && docker run -d --name quantmind-redis-lan-bridge \
  --restart unless-stopped --network host --memory 512m \
  -e REDIS_LAN_BIND_IPS=192.168.31.68,192.168.31.56 \
  -e REDIS_LAN_ALLOW=192.168.31.13,192.168.31.68,192.168.31.56,192.168.31.250 \
  -v /home/zbox/projects/quantmind/deploy/redis_lan_bridge.py:/bridge.py:ro \
  python:3.10-slim-bookworm python3 /bridge.py
```

## 根因二：Redis 里的运行时桥配置会覆盖 `.env` 和容器 env

`trade:tdx_config:runtime`（trade Redis **db2**）持久化着 `bridge_url` / `bridge_token`。
trade 服务启动时 `apply_runtime_config()`
（`backend/services/trade/routers/tdx_config.py`）把它**写回** `settings` / `os.environ` /
`tdx_pusher`。

所以容器 env 与仓库 `.env` 都改成 `.250` 后，日志仍然打印：

```
[TdxSync] 通达信账户同步任务启动, interval=30s, bridge=http://192.168.31.13:8550
```

`QmtBridgeClient` 构造时读到被覆盖的 `.13` → 每轮 `ConnectTimeout`。
**识别特征：`docker exec` 起的新进程跑同样代码能连通，常驻任务却不行。**

**修复**（token 用 `.env` 里的 `TDX_BRIDGE_TOKEN`）：

```bash
redis-cli -n 2 set trade:tdx_config:runtime \
  '{"bridge_url": "http://192.168.31.250:8550", "bridge_token": "<TDX_BRIDGE_TOKEN>"}'
docker restart quantmind        # 或走管理员 PUT /tdx/config（即时生效并持久化）
```

## 同步处理

  （本次 1,620 条，全部只读；订单类 0 条，硬护栏未触发）

  无需手动 umount —— 验证：`ls /mnt/tdx-shared` 秒回、容器内同路径可见

## 验收

```bash
curl -s http://192.168.31.250:8550/api/v1/health | grep -o '"online": *[a-z]*'   # true
docker logs --since 5m quantmind | grep "账户快照已落库"                          # 每 30s 一条
docker exec quantmind-redis redis-cli -n 5 ttl qm:qmt:pipe:heartbeat              # < 30
docker exec quantmind-redis redis-cli -n 0 hget qm:qmt:quote:backup:status bridge_ok
```

## 排查口诀（下次先看这三样）

1. `docker logs quantmind-redis-lan-bridge | grep 拒绝` —— 新 IP 是否被白名单拦了
2. `redis-cli -n 2 get trade:tdx_config:runtime` —— 运行时桥配置是否还是旧地址
3. `docker exec quantmind printenv TDX_BRIDGE_URL` —— 只证明容器 env，**不证明进程内生效值**

> 另注：`/api/v1/account/query`（不带 `source`）返回的是**通达信 mock 账户**，
> 与 QMT 无关；它返回空账户（`account_id=0`）会让 `trade:bridge:outage:open` 持续刷新，
> 不要拿它判断 QMT 是否在线。
