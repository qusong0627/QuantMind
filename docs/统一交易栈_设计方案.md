## 一、为什么要重构：现状的"乱"从哪来

一句话：**系统里没有一个"唯一契约"，每条链路各定义各的**。具体表现（均为实测）：

| 乱象 | 现状 | 根因 |
|---|---|---|
| 四条选股链路各选各的 | `/selection` 三层过滤、模拟盘 TopK、TDX 阈值 2.2、DSL 筛选 | 没有统一的「信号→选股」契约 |
| 同一个 admin 两套账户 | Redis `simulation:account:default:1`（有 27 持仓）与 `:00000001`（空） | 没有统一的身份归一 |
| 账户卡片与资金曲线对不上 | 卡片读 int(1)，曲线读原始 sub(00000001) | 同上 |
| 收益曲线凭空 +100 万 | 跨市场资产相加、initial_capital 只算一份 | 没有统一的账本口径 |
| 五种策略格式互不兼容 | Qlib config / minibt / Lab SDK / 沙箱 on_tick / AI 模板 | 没有统一的策略契约与注册表 |
| 参数配了不生效 | min_score 死配置、execution_config 被 save 重置 | 没有"参数唯一存放处 + 生效校验" |
| 模拟成交价是昨收 | 托管按日线分区 close 撮合 | 没有统一的取价契约与陈旧价守卫 |
| 回测通过≠能上模拟≠能上实盘 | 三条链路互不衔接 | 没有"晋级"状态的单一事实源 |
| PG 台账全空、Redis 是唯一事实源 | ledger 表 0 行 | 没有强制"成交必落账" |

**重构判断**：不推倒重来（QuantDB 五市场数据、qlib 缓存、训练管线、QMT 桥都是资产），而是**先立契约、再收链路**。同时为长期目标（tick 级数据、实时推理、高性能回测、盘中实时监控）预留清晰接口，避免二次返工。

## 二、设计原则（七条铁律）

1. **单一契约**：只有四个跨模块接口——`Signal`（模型→策略）、`Strategy Spec`（策略定义）、`Order/Fill`（策略→执行）、`Ledger`（资金事实源）。新功能先问"改哪张契约"，不允许绕过契约新增链路。
2. **回测-模拟-实盘同构**：同一个撮合内核 + 同一套交易规则 + 同一个状态机；三种环境只在「数据供给」与「执行端点」上有差异。
3. **阈值一律用分位/rank 表达**：禁止硬编码绝对分数（`score >= 0.10`），只能用 `rank_pct >= 0.98` 或自适应分位。
4. **身份与口径在边界处归一，一次且唯一次**：`tenant/user/market/symbol` 进系统即归一。
5. **每步幂等、可重跑、可下钻**：`run_id` 贯穿全链路，数字可逐层下钻到源头。
6. **快慢分离**：批量轨（T+1，分钟级）与实时轨（盘中秒级，后期 tick 毫秒级）用**不同技术栈**，但共享**同一套契约与规则内核**。不在一条链路上混两种性能目标。
7. **共享计算、用户轻量**（设计复盘中补充）：面向消费者规模——全市场信号计算、盘中热集推理、行情扫描均为**系统级共享计算**（成本与用户数脱钩）；用户层只承载"策略参数应用 + 账户 + 通知"，禁止用户触发独立的全市场重算。越贵的计算越往上收，越个性化的越往下放。

## 三、总体架构：一条主干 + 两条时间轨 + 七层

### 3.1 批处理轨（T 日盘后 → T+1 执行，主链路）

```
T日盘后                               T+1 盘前                T+1 盘中            T+1 盘后
┌──────── ┌────────┐ ┌──────────┐ ┌──────────────┐ ┌────────────┐ ┌──────────┐ ┌──────── ┐
│L0 数据 │→│L1 特征 │→│ L2 模型  │→│ L3 信号总线  │→│ L4 策略    │→│ L5 风控  │→│ L6 执行│→ L7 账本
│同步    │ │计算    │ │ 批量推理 │ │ 落库+就绪标记 │ │ 选股→持仓  │ │ 闸门+仓位│ │ 撮合   │  结算/对账
└────────┘ └──────── └──────────┘ └──────────────┘ └────────────┘ └──────────┘ └────────┘ ┘
  15:10      15:40       16:30         就绪徽章         08:30 计划     风控配置     09:30-14:57  15:10
```

### 3.2 实时轨（盘中，P6 起启用）

```
盘中 09:15–15:00（快照 3s 级；tick 级为 P7 预留）
行情快照流 → 实时特征(增量) → 热集推理(持仓+候选+异动) → 实时信号 ─┐
新闻/RSS 流 → 情绪打分 → 事件分级 ────────────────┐               │
指数/涨跌停/成交额 → 日内市场状态 ────────────────┼→ 盘中情报总线 ─→ L5 风控闸门 → L6 执行
量价异动/账户异常 → 识别引擎 ────────────────────┘   (统一事件流)  │        (模拟/实盘)
                                                                  └→ L4 策略(事件驱动/情绪过滤)
```

### 3.3 七层：现状资产 → 目标 → 关键动作

| 层 | 现状（复用） | 目标 | 关键动作 |
|---|---|---|---|
| L0 数据 | QuantDB 等五市场 parquet、qlib 缓存、定时同步 | 批处理不变；**新增 L0.5 tick/L2 层**（10GB/日，见《L2数据与实时推理_工程方案》） | 数据健康度心跳进交易台 |
| L1 特征 | 151 维特征 parquet | 批处理不变，**新增增量特征**（real-time 复用同一因子定义） | 特征版本号写入 run manifest |
| L2 模型 | 训练管线、模型注册表、推理脚本、model_ic_monitor | **批量推理 + 热集实时推理**共用模型产物（ONNX 导出） | IC 门禁；实时推理服务（§八） |
| L3 信号 | `engine_signal_scores`、就绪服务、Redis 标记 | **Signal 契约**（§4.1），加 `source: batch\|realtime` 与精度时间戳 | rank/pct 列、市场列；阈值分位化 |
| L4 策略 | 5 种格式、strategy_storage、回放、沙箱 | **Strategy Spec 契约 + 注册表**（§4.2） | 收敛 2 格式；状态机 DRAFT→VERIFIED→SIM→LIVE |
| L5 风控 | risk_lock、mirror 闸门、QMT 止盈止损、买入过滤（缺） | **风控链 + 识别引擎**（§五） | 买入前过滤、veto、通道流量风控、异常识别 |
| L6 执行 | 模拟撮合（3 套入口）、QMT 镜像、TDX 推送 | **Order 契约 + 单一路由 + 执行内核 SPI**（§4.3、§八） | OrderRouter；撮合规则单实现；保真度阶梯 |
| L7 账本 | Redis 账户 + 空 PG 台账 + 快照 | **Ledger 契约**（§4.4） | PG 唯一事实源；成交必落账；自动对账 |

**三条横向能力**（贯穿全部七层，均为契约扩展，不新增链路）：
- **多市场可插拔**：Market Adapter SPI，市场差异唯一出口（见《多市场可插拔架构_设计方案》）
- **评估与打分**：五张评分卡驱动晋级/降级/告警（见《评估与打分体系_设计方案》）
- **LLM/Agent**：只作为信号源与工具接入既有契约，永不直达下单（见《LLM与Agent接入_设计方案》）

## 四、四张契约（核心）

### 4.1 Signal 契约（模型 → 策略的唯一接口）

```sql
-- engine_signal_scores 增列（兼容旧读，视图过渡）
run_id        text    -- 推理批次
trade_date    date    -- 信号生效日（T+1）
market        text    -- CN/HK/US/FUTURES/CRYPTO（新增）
symbol        text    -- 前缀式归一（写入即归一）
model_id      text
universe_tag  text
score_raw     float8  -- 模型原始分（仅研究用）
score_rank    float8  -- 截面分位 0..1（新增，**策略只允许用它**）
side          text    -- BUY/SELL/HOLD
confidence    text
source        text    -- batch | realtime（新增，实时轨信号）
ts            timestamptz -- 精确产生时间（实时轨用，新增）
```

- **策略与风控阈值只允许引用 `score_rank`/分位**；绝对分数只做展示。
- `side`（信号）与选股（策略对信号的使用）**解耦**，互不覆盖。
- 就绪标记 `qm:signal:ready:{market}:{trade_date}`：全量落库+校验通过才置位；实时轨用 Redis Stream 推送（同契约序列化）。

### 4.2 Strategy Spec 契约（策略定义唯一形态）

```jsonc
{
  "id": "stg_cn_0007", "version": 3,
  "name": "A股-动量低吸v3", "market": "CN", "format": "params",   // params | minibt
  "universe":  { "pool": "cn_main_board", "exclude": ["ST","suspended","limit_up","limit_down","new_listing_60d"] },
  "selection": { "source": "model:mdl_xxx", "order_by": "score_rank", "topk": 10, "min_rank_pct": 0.98 },
  "portfolio": { "weight_mode": "equal", "max_position_pct": 0.15, "max_positions": 8 },
  "risk":      { "stop_loss": -0.05, "take_profit": 0.08, "max_hold_days": 5,
                 "veto": { "fundamental": true, "news_event": true },      // 新闻风险事件 veto（§六）
                 "buy_filters": ["rise_from_low<=50%","open_gap<=4%","bias5<=7"] },
  "execution": { "window": "14:45", "price_mode": "auto", "slippage_bps": 5 },
  "code": null,                      // format=minibt 时存在
  "status": "SIM",                   // DRAFT→VERIFIED→SIM→LIVE
  "evidence": { "backtest_run_id": "...", "sim_days": 12, "sim_tracking_error": 0.8, "speed_backtest_id": "..." }
}
```

- **只保留两种格式**：`params`（声明式，覆盖 90%）与 `minibt`（DSL 代码策略）；现存 5 种一律收敛/转换；AI-IDE 生成物强制落这两种。
- `strategy_storage.py` 唯一读写入口（修复 async delete、补版本/状态机）；保存即校验（schema + AST + 1 天试运行）。
- **参数锁**（借鉴 WonderTrader 组合盘配置 + KHunter param_lock）：改线上策略参数必须显式升版本。
- 策略晋级必须有 `evidence`：回测报告 + 模拟天数 + 模拟-回测跟踪误差。

### 4.3 Order / Fill 契约（策略 → 执行的唯一接口）

```jsonc
{ "client_order_id": "stg_cn_0007-20260916-0001",   // 幂等键
  "strategy_id": "stg_cn_0007", "mode": "SIM",      // SIM | SHADOW | REAL
  "market": "CN", "symbol": "600036.SH",
  "side": "buy", "qty": 100, "type": "market|limit", "limit_price": null,
  "source": "rebalance|sltp|manual|mirror|event", "reason": "rank 0.99 入选，等权建仓" }
// Fill
{ "...", "price": 41.83, "price_source": "tick|snapshot|today_bar|prev_close|fallback",
  "fees": {"commission": 5, "stamp_duty": 0, "transfer": 0.04}, "filled_at": "..." }
```

- **一个 OrderRouter**：所有下单（模拟/影子/实盘/手动/沙箱/镜像/实时事件）经过它；持账户锁、幂等、状态机。
- **撮合规则单实现**：`market_rules.py` + `ashare_matcher.py` 提升为全模式共用内核。
- 取价契约：`auto` = 实时 tick/快照 → 当日 K → 昨收，**必标 `price_source` + 陈旧价守卫**。

### 4.4 Ledger 契约（唯一资金事实源）

- PG 唯一事实源（accounts/lots/cash_ledger/orders/fills/daily 加 `mode` 列共用）；Redis 为可重建热缓存（按市场重建）。
- **成交必落账、单事务**；任何模式漏写台账视为 bug。
- 市场账户是账本、用户总览是聚合视图（initial_capital 按市场求和）。
- 自动对账：日内（Redis ↔ PG）、日终（模拟 ↔ 影子 ↔ 券商），差异红点告警。

## 五、风险管理体系（独立一层，含识别引擎）

> **生产级细则见《风险控制体系_设计方案.md》**：七级防线（系统/账户/策略/订单/标的/市场/数据模型）、
> 完整规则库、四级状态机（NORMAL→CAUTION→RESTRICT→HALT）、fail-closed 语义、影子模式、演练与审计。
> 本节仅列总览，实施以该文档为准。

| 时机 | 闸门 | 配置 | 现状 |
|---|---|---|---|
| 事前·标的 | ST/停牌/涨跌停/次新/流动性/北交所 | universe.exclude | 部分有，口径需统一 |
| 事前·否决 | 基本面/事件/**新闻风险事件** veto | risk.veto + `risk_flags` | 坑位已有，未接线 |
| 事前·形态 | 买入前 K 线过滤（20日涨幅、开盘跳空、BIAS5、量能确认） | risk.buy_filters | **缺**，移植 KHunter 规则 |
| 事前·仓位 | 单票/行业/总仓上限；Kelly / 波动率目标 | portfolio.* | 仅等权+上限 |
| 事中·禁买 | 风控禁买锁、风险状态降仓 | Redis 热配置 | 已有（risk_lock） |
| 事中·偏离 | 模拟→实盘镜像价格偏离闸门(2%) | mirror 配置 | 已有 |
| 事中·**合规流量** | **撤单率/下单频率/单通道并发**（借鉴 WonderTrader 通道流量风控） | 通道配置 | **缺**（QMT/券商合规必需） |
| 事中·市场 | 日内 regime 路由（大盘状态→仓位系数/策略切换） | 全局配置 | 缺（§六市场状态服务提供输入） |
| 事中·止损 | 止损/止盈执行器（QMT sltp 已有，模拟侧补齐） | 策略 risk | 部分有 |
| 事后 | 日对账、IC 监控、归因、**异常识别** | 自动 | 部分有（未接线） |

**识别引擎（异常检测，新增）**——统一产出「告警/否决/降仓」三类动作：

| 类别 | 检测对象 | 例子 | 动作 |
|---|---|---|---|
| 市场异动 | 个股/板块量价 | 放量异动、封板/开板、板块联动 | 告警 + 策略事件信号 |
| 账户异常 | 交易行为 | 频繁撤单、自成交、单票集中度飙升 | 告警 + 限频/禁买 |
| 数据异常 | 行情/特征 | 价格跳变、缺口、特征漂移(PSI) | 暂停该标的 + 告警 |
| 模型异常 | 预测分布 | IC 骤降、分数分布坍缩 | 降仓/停用建议（对接 model_ic_monitor） |

原则：风控与识别都是**链上插件**，配置一处生效、生效状态与今日拦截数在交易台可见可审计。

## 六、盘中情报总线（Intelligence Bus，P6）

三路输入 → 统一事件流 → 双消费（风控闸门 / 策略）：

### 6.1 新闻情绪监控（分钟级）
已有资产：Huntly/RSS 聚合 + **FinBERT 中文金融情感**（权重已修复，见 `docs/FinBERT 中文金融情感模型.md`）。
链路：新闻流 → 去重/时效过滤 → **实体链接**（个股/行业/概念）→ FinBERT 打分 → 事件分级（中性/利好/利空/风险事件）→ 输出：
- 个股/行业情绪分（滚动窗口）→ 策略可作过滤/加权
- **风险事件告警**（立案/处罚/退市风险/暴雷）→ 风控 **veto 直连**（策略配置 `risk.veto.news_event=true` 时生效）
- 盘中情绪突变（热度+极性骤变）→ 告警 + 异动识别输入

### 6.2 市场状态服务（3s–1min）
日内指标：指数趋势（MA/ADX）、涨跌家数、涨跌停家数、成交额/量比、板块 RST（相对强度）、情绪指数。
输出：**日内 regime**（与日频 `market_state` 同口径同枚举），供 L5 风控（仓位系数）与 L4 策略（开关/切换）消费——把 KHunter 的 ADX regime 路由做成日内+日频双层。

### 6.3 异动识别（见 §五识别引擎）
统一事件结构（Redis Stream / PG 事件表）：
```jsonc
{ "ts": "...", "type": "news|regime|anomaly", "market": "CN",
  "targets": ["600036.SH"], "level": "info|warn|critical",
  "payload": {...}, "actions_hint": ["veto","alert","downsize"] }
```

## 七、性能体系：三层回测 + 性能预算

**要求：快（研究迭代）+ 真（验收口径）+ 深（tick 保真）三者分层，各用各的引擎，共享契约。**

| 层 | 引擎 | 数据 | 用途 | 目标性能（验收） |
|---|---|---|---|---|
| **R1 向量化研究** | qlib / polars（现有） | 日频 | 因子/参数快速扫描 | 全市场 5000 股 × 5 年 < 60s |
| **R2 事件驱动精确** | 现有 qlib step / minibt | 日频+快照 | 晋级验收（撮合全规则） | 同规模 < 10 min |
| **R3 tick 回放**（P7） | 执行内核 SPI（§八） | tick/L2 | 执行算法/队列建模 | 单标的单日 < 1s |

规则：**R2 是晋级唯一标准**（R1 只用于筛选）；R2 与模拟盘共用撮合内核（§二铁律 2），并有**回测-模拟一致性测试**（同策略同区间订单序列 diff=0）作为自动验收。
策略参数扫描（策略优化）走 R1 出候选 → Top-N 进 R2 精验 → 通过才进 evidence。

## 八、实时与 tick 路线（长期预留）

### 8.1 数据层 L0.5：tick / L2

> **10GB/日 的完整工程规划见《L2数据与实时推理_工程方案.md》**：量级测算（峰值 3–7 MB/s、年增 2.4TB）、
> 五层存储留存、六项数据质检（含订单簿重建对账）、实时链路分片与延迟预算（端到端 <2s）、
> 实时买卖闭环与 P7 七步里程碑。

- 存储：按天分区 parquet（沿用 QuantDB 分区范式）+ DuckDB 直查；热点回放可转 mmap/Arrow 内存格式。
- 内容：逐笔成交（trade）、逐笔委托（order）、3s 快照（含十档）。已有基础：TDX 桥 L2 通道、L2 特征管线。
- **时间对齐契约**：tick 时间戳统一 ns 精度、交易所时钟口径、与日线/快照的换算关系写入数据字典（防"分钟复权双重缩放"类事故重演）。

### 8.2 实时推理（盘中）
- 分层：全市场批量（T+1，已有）→ **热集实时**（持仓 + 候选 + 异动股，约 300–800 只）→ 事件触发（新闻/异动即时推理）。
- 技术：**增量特征**（复用同一份因子定义，避免全量重算）+ **ONNX Runtime 模型服务**（训练产物导出）+ Redis Stream 信号总线。
- 与批量信号同契约（§4.1 `source=realtime`）；性能预算：热集 500 只单轮推理 < 1s（3s 快照节拍内完成）。

### 8.3 模拟接近实盘：撮合保真度阶梯
| 级别 | 数据 | 撮合方式 | 覆盖场景 | 计划 |
|---|---|---|---|---|
| F1 日K | 日线 | 收盘/开盘价 + 滑点 + 涨跌停/T+1/费用 | 研究回测 | 有 |
| F2 快照 | 3s 盘口 | 现价 + 盘口深度约束 + 涨跌停排队 + 部分成交 | **模拟盘主用**（P6 达标） | 待建 |
| F3 队列 | tick/L2 | 队列位置模型 + 委托排队 + 延迟建模 | 执行算法/tick 策略 | P7 |

模拟接近实盘的验收指标（持续度量，显示在交易台）：
- 成交价偏差（模拟 vs 影子/实盘同单）分布
- 成交率/部分成交比例
- 滑点实现值 vs 配置值
- **模拟-实盘跟踪误差**（同策略同期收益差）——晋级实盘的硬门槛输入

### 8.4 执行内核 SPI（长期选型隔离）
```
ExecutionCore 接口:  on_market(events) / submit(Order) / cancel / fills()
实现（按需插拔，契约不变）:
  ├─ DailyCore    (Python，现有 matcher 提升)          —— A股/多市场日频
  ├─ SnapshotCore (Python asyncio，3s 快照级)          —— 盘中模拟/实盘预演
  └─ TickCore     (后期三选一，见 §十三)                —— tick/队列级
```
上层（策略/风控/账本/前端）只依赖 SPI 与 Order/ Fill 契约，**换内核不动上层**——这是"想长远"的关键保险。

## 十二、迁移路线（总表 + MVP 收敛）

### 12.1 MVP 定义（一期最小可信产品，建议 6–10 周）

**目标**：A 股单市场，「每天自动选股 → 策略 → 模拟盘 → 看得懂、有证据」对消费者可用。

**收录**：P0 全部（含维护基建）→ P1 → P2 → P3/P4 的核心子集 → 回测体检 + 选股评分 → L1 哨兵推送 → 今日交易台 v1。

**明确推迟**（写清原因，防范围蔓延）：L2/tick（数据未接入）、LLM 信号（需评估体系先跑通）、多市场扩展（A 股闭环验证后再复刻）、执行算法/组合优化（机构台阶，有 Sh 剩余再上）、实时轨（依赖 P2 完成 + L0.5 数据）。

### 12.2 全量路线表

| 阶段 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| **P0 止血+维护基建** | 安全三件；身份归一；快照修正；EOD worker；**一键体检脚本+断言集；12 条回归测试；错误自定位；代码地图 v1** | — | 同用户任意入口数字一致；体检脚本可跑；回归进 CI |
| **P1 契约化** | 四契约（增列+视图兼容）；今日交易台 v1；调度表统一 | P0 | 信号 rank 列回填；交易台数字可下钻 |
| **P2 执行统一** | OrderRouter；撮合单实现；取价契约+陈旧价守卫；**退出规则单一实现**（策略/风控/止损执行器三方共用） | P1 | 回测-模拟一致性 diff=0；price_source 标注 100% |

### 12.3 关键依赖说明（防踩空）

1. **F2（快照级撮合）依赖 L0.5 快照留存**——没有历史快照，F2 只能"实时快照"、无法回放，回测仍停留在日线。
2. **实时轨依赖 P2 先完成**——执行没统一就上实时 = 把混乱乘以 3 秒节拍。
3. **LLM 信号依赖 P4 评估体系**——没有 IC 评估能力的信号源不许上生产（六铁律之一）。
4. **多市场依赖契约稳定**——契约还在改就复刻市场 = 复刻混乱。

每阶段独立可发布、可回滚（旧链路保留开关直到新链路验收）。

## 十三、框架调研结论：借语义，不借代码

**总原则**：现有资产（QuantDB 五市场数据、qlib 缓存、训练管线、QMT/通达信桥、多租户 Web 平台）与任何外部框架的数据层/执行层都冲突，整体迁移=重写。借语义、抄规则、留 SPI。

| 框架 | 状态（2026） | 借鉴什么 | 为什么现在不整体用 |
|---|---|---|---|
| **WonderTrader**（MIT，wtpy） | 活跃，v0.9.9 | ① **SEL 异步引擎**（多因子选股/截面多空，注册式重算调度）；② **离合器机制**（信号/执行分离，可断开执行不影响策略）——我们 P2 的 OrderRouter + 风控解耦就按此语义；③ **M+1+N 账户架构**（组合→多账户倍率，后续多账户直接抄）；④ **通道流量风控**（撤单率/频率，QMT 合规必需）；⑤ mmap+UDP 广播的行情分发（tick 时代参考） | 数据层自有格式（mmap+MySQL）与 QuantDB 冲突；股票实盘接口全是机构通道（XTP/奇点/ATP/OES），与我们的 QMT/通达信桥不搭；Web 平台集成成本高。**列为 P7 TickCore 候选之一** |
| **hftbacktest**（Rust+Python） | 活跃 | ① **队列位置模型 + 部分成交**（F3 保真度的现成参考实现）；② tick/L2 回放架构；③ 数据融合（BBO+深度重建订单簿） | 面向加密市场；A 股 L2（3s 快照+逐笔）需自适配数据与规则。**P7 TickCore 候选之二** |
| **RQAlpha** | 活跃（2026-05） | A 股撮合规则与 Mod 扩展点（P2 对照） | 开源版限非商业；数据层冲突 |
| **Hikyuu** | 非常活跃（2.8.2, 2026-08） | 七组件化（市场环境/信号/止损/资金管理）与 §五 风控链同构 | C++ 内核嵌不进 Python 栈 |
| **vn.py / VeighNa** | 活跃（4.0 + Alpha158） | 若扩期货/期权，仅引其**网关层**做独立服务 | 全栈重叠 |
| **KHunter / a-share-quant-selector** | 个人向工具 | **规则层直接移植**：买入前 K 线过滤、入池规则参数化、ADX regime 路由、Kelly 仓位、参数锁 | 架构不适用 |
| **QuantConnect Lean** | 活跃 | "一份代码回测/实盘同构"哲学（铁律 2 来源） | C# 核心，A 股非主场 |

**P7 TickCore 选型矩阵**（届时按实测决定）：

| 候选 | tick 回测性能 | 队列模型 | A股适配成本 | 实盘能力 |
|---|---|---|---|---|
| 自研 Rust 内核 | 高 | 自建 | 可控 | 接我们自己的 OrderRouter |
| WonderTrader HFT | 高 | 内置 | 数据格式 ETL + 侧车服务 | 期货强、股票机构通道 |
| hftbacktest | 高 | 内置（最好） | 数据与规则自适配 | 只回测 |
