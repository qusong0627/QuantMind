# L2 数据与实时推理工程方案（10GB/日 → 实时买卖）

> 版本：v1（2026-09-15）　配套：`docs/统一交易栈_设计方案.md`（v3）、`docs/风险控制体系_设计方案.md`
> 场景：后期接入 A 股 L2 数据（**约 10GB/日**），据此做**实时推理、实时买卖**。
> 已有资产：TDX 桥 L2 通道（tqcenter）、`l2-sata-fuse` 容器、L2 特征训练管线、211 个 L2 因子检验结论（VPIN 最强、T1→T10 持续增强）。

---

## 一、量级测算（先算账，再设计）

| 项 | 数值 | 推演 |
|---|---|---|
| 日落地量 | **10 GB/日**（原始/压缩） | 用户给定 |
| 盘中均速 | ≈ 0.7 MB/s | 10GB ÷ 4h 交易时段（14400s） |
| 峰值（开盘/尾盘 5–10x） | **3–7 MB/s** | 单节点可承受；瓶颈不在带宽在**解析 CPU** |
| 年增量（243 交易日） | ≈ **2.4 TB/年** | 需分层留存策略 |
| 解析后（parquet+zstd 重压） | ≈ 原始 40–60% | 分区裁剪后查询高效 |
| 特征层（分钟级聚合） | ≈ 1–2 GB/日 | 供训练/推理的高价值层，可长期保留 |
| 逐笔重建订单簿（实时） | 全市场内存 ≈ 数十 GB | 只对**热集**（500 只）常驻内存：≈ 5-10 GB |

**结论**：10GB/日在"存储+批处理"上是中等规模（单机 SSD + DuckDB 足够起步）；真正需要精心设计的是**实时链路的解析与特征更新**，以及**分层留存**。

## 二、存储分层（L0.5 数据层）

| 层 | 内容 | 格式 | 留存 | 介质 |
|---|---|---|---|---|
| Raw | 采集原始流（先落盘，防丢） | 压缩文件/追加日志 | 30 天 | SSD |
| Parsed | 逐笔委托/逐笔成交/快照，按 `date/symbol` 分区 | parquet + zstd | 13 个月在线 | SSD→HDD 自动迁移 |
| Features | 逐笔衍生特征（分钟/快照聚合） | parquet 分区（沿用 QuantDB 范式） | 永久 | SSD |
| Cold | Parsed 历史归档 | parquet | 3 年+ | 对象存储/HDD |
| Mem | 热集订单簿/特征快照 | Arrow/mmap | 实时 | 内存 |

约定：
- **分区键与 QuantDB 完全一致**（`date/symbol`），查询统一走 DuckDB（`hub._read_partitioned` 范式，防"dt 列遮蔽"类事故重演）。
- schema 版本化：逐笔字段随交易所/供应商升级变更 → schema 版本号写入每个分区元数据，解析器按版本分派。
- **保留策略可配置**：过期数据自动降冷（脚本化，跑在 EOD 之后，不占用盘中资源）。

## 三、批处理管线（T 日盘后）

```
采集落地(Raw) → 解析规范化(Parsed) → 数据质检 → 特征计算(Features) → 质检报告 → 可供训练/回放
```

### 3.1 数据质检（每日必跑，不合格数据不进特征层）

| 校验 | 方法 | 处置 |
|---|---|---|
| 序列号连续性 | 逐笔序列号 gap 检测 | gap > 阈值 → 该标的当日标记"低质量" |
| 时间戳单调 | 时间戳回归检查 | 乱序修正/丢弃 |
| 笔数分布 | 各标的笔数 vs 20 日均值 ±5σ | 异常告警（可能缺数据） |
| **订单簿重建对账** | 用逐笔委托+成交重建订单簿，与官方快照比对 | 十档价格/量偏差 < 阈值；超标 → 当日数据停用并排查 |
| 涨跌停一致性 | 逐笔极值 vs 日线涨跌停价 | 不一致告警 |
| 覆盖度 | 标的数 vs 全市场 | 缺失清单 |

### 3.2 特征计算（复用已有 211 因子结论）

- 三层输出：**逐笔级**（事件流特征）→ **分钟级**（聚合特征，主训练层）→ **日级**（汇总特征，并入现有 151 维）
- 重点因子（已有检验结论）：VPIN（最强、T1→T10 持续增强）、主买/主卖占比、大单净流入、盘口失衡、撤单率、委托队列长度
- 计算引擎：DuckDB SQL + polars（批），与实时链路**共用同一份特征定义**（抽成共享模块，禁止两处各写一遍——防"训练/推理口径漂移"）

## 四、实时链路（盘中）

```
L2 实时流 → 消息总线(Redis Stream/自建队列) → ①解析/规范化(多进程分片)
   → ②热集内存特征引擎(增量更新, per-symbol 状态) → ③热点触发判定
   → ④热集推理(ONNX, 批量) → ⑤实时信号 → ⑥风控(§风控体系) → ⑦下单(OrderRouter)
```

### 4.1 分片与并发
- 解析按 `hash(symbol) % N` 分片多进程；特征引擎每分片一个进程（避免 GIL）；N 按 CPU 核数（默认 4–8）。
- 热集（持仓+候选+异动）常驻内存维护订单簿与滚动特征；冷标的**只落盘不维护状态**（按需加载）。

### 4.2 延迟预算（端到端目标 **< 2s**，决定可做的策略频率等级）

| 环节 | 预算 | 备注 |
|---|---|---|
| 行情到达 → 解析完成 | < 50 ms | 分片并行 |
| 特征增量更新 | < 30 ms | 只算变化的标的 |
| 触发判定（异动/阈值） | < 10 ms | 事件驱动，非全量扫描 |
| 热集推理（≤500 只） | < 100 ms | ONNX 批量 |
| 风控检查 | < 1 ms/单 | §风控 L3 |
| 下单到柜台 | < 1 s | QMT 通道实测；**这是最大头，需压测** |
| **合计** | **< 2 s** | 对应策略频率：分钟级可靠、秒级边缘、毫秒级不做（诚实边界） |

### 4.3 与批量轨的关系
- 实时信号 `source=realtime` 写入同一 Signal 契约（含 tick 精度时间戳）；策略可声明"仅实时 / 仅批量 / 混合"。
- 实时轨的任何信号都必须可被**盘后回放复现**（同一数据、同一特征、同一模型 → 同信号），否则视为 bug（可复现性是实时系统的生命线）。
- **tick 回放引擎（TickCore）**：用 Parsed 层做历史回放，验收实时策略；这是"实时策略上线前"的唯一准入路径。

## 五、实时决策闭环（"根据 L2 实时推理、买入卖出"）

| 环节 | 设计 |
|---|---|
| 触发 | 事件驱动（异动/大单/盘口突变/新闻）+ 定时（每 3s 快照）双通道；全市场扫描降频到分钟级 |
| 决策 | 模型输出（热集）→ 策略规则（§7 策略契约）→ 目标持仓调整 → Order 契约 |
| 风控 | 全量走 §风险控制体系（L3 订单级 + L6 数据级必有：tick 跳变、行情陈旧、盘口异常） |
| 执行 | 实盘走 OrderRouter → QMT；模拟走 SnapshotCore（F2 快照级撮合，含盘口深度/部分成交） |
| 节流 | 单账户日内实时下单上限（防高频失控）；同标的 N 秒冷静期；与风控 L3 频率/撤单率共享计数 |
| 熔断 | 实时策略独立"日内亏损限额"（比日频更严，如 -1.5% 停止） |

## 六、工程里程碑（P7 拆解）

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1. L2 落地 | Raw 采集→Parsed 解析→分区存储 | 连续 5 交易日全量落盘、质检通过 |
| 2. 质检体系 | §3.1 六项校验自动化 | 订单簿重建对账偏差达标报告 |
| 3. 特征层 | 逐笔→分钟特征（复用 211 因子结论） | 特征与训练管线打通、IC 复现 |
| 4. 回放引擎 | TickCore v1（单标的单日回放 <1s） | 实时策略历史验收可行 |
| 5. 实时特征 | 内存特征引擎 + 分片 | 延迟预算 §4.2 实测达标 |
| 6. 实时推理 | ONNX 热集推理接入 | 端到端 <2s 实测；信号可盘后复现 |
| 7. 实时交易 | 风控+OrderRouter 接入，模拟先行 | 模拟跑满 N 日 → 小仓实盘 |

## 七、开放问题

1. L2 数据源形态：TDX 桥推送（逐笔/快照齐全度）vs 供应商落地文件？决定解析器与时效。
2. 10GB/日 是"原始"还是"已解析"？影响存储分层容量规划。
3. 实时推理的模型选择：复用日频模型（特征需对齐到日内）vs 训练专用日内模型（L2 特征为主）——建议**先复用+特征对齐**，再迭代专用模型。
4. 柜台时延实测：QMT 通道下单-成交回执 P99（决定端到端预算里最大项）。
