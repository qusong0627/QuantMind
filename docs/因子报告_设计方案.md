# 因子报告（Alphalens 式）设计方案

> 目标：把「这一堆因子到底哪个能用」从脚本结论变成**一页可看的标准报告**——
> （Alpha 库 429 个，外加 QuantDB 的 L1 110 / L2 211 / L1+L2 321 个）
> 分位收益、换手率、相关性去重三件事一屏回答，落在技能中心「因子报告」页签。
>
> 缘起：对照开源框架选型（backtrader/vectorbt/zipline/finrl 那类）时确认的一个真空白 ——
> 我们有 429 个因子、有 IC 检验脚本，但没有 Alphalens 那种**成体系的因子体检产出**。

---

## 一、结论先行

1. **数据全都现成**：QuantDB 的四个 A 股因子源都接进来了 ——
   | 数据集 | 因子数 | 分区 | 体积 | 标签来源 |
   |---|---|---|---|---|
   | `alpha_library` | 429（Alpha158 158 + Alpha101 101 + GTJA191 170） | 2599 | 19 GB | 独立标签表 `alpha_library_labels`（fwd_ret_1/2/5/10/20） |
   | `l1_factors` | 110（量价/换手/波动等） | 2599 | 8.8 GB | 本表 close 的 T+k 收益 |
   | `l2_factors` | 211（逐笔微观结构） | 1133 | 9.7 GB | 同上 |
   | `l1_l2_factors` | 321（= 110 + 211） | 1133 | 14 GB | 同上 |
   L1/L2 用「本表 close 在 T+k 分区的收盘价」算前瞻收益，与训练侧 `features_daily.return_Nd`
   同口径（`return_1d[T] == pct_change[T+1]`，见 `docker/training/data/loading.py:117`）。
2. **一次遍历算完三件事**：把每日横截面取秩后，秩矩阵的 `RᵀR` 累加得到因子秩相关矩阵，
   秩分组得到十分位组合收益与换手 —— 一趟扫描同时产出，实测 alpha 库 1138 个交易日 /
   8 进程 / **150 秒**（L1 约 100 秒、L2/L1+L2 各约 3 分钟）。
3. **快照 + 明细序列两层**：排行与相关性走快照 JSON；单因子明细（分位净值、IC 序列、
   换手序列）在**同一次构建**里落成 `factor_series.parquet`（逐日 × 逐因子）——
   明细接口从「扫 250 个分区 ~2.4s」降到 **~0.14s**（实测 15 倍）。
4. **不做的事**：不引入新依赖（numpy 双排序 + pyarrow 列裁剪），不改因子数据，
   不替换既有 IC 脚本（本脚本窗口指标与它同口径，可用于交叉验证）。

## 二、口径（写死在这里，避免各处解释不一致）

| 指标 | 口径 |
|---|---|
| 秩 IC | 每日横截面因子秩 vs 前瞻收益秩的 Pearson（= Spearman），窗口内按日均值 |
| ICIR | IC 均值 / IC 标准差；t 值 = ICIR × √样本数 |
| IC 胜率 | IC > 0 的交易日占比 |
| 分位收益 | 按因子值升序等分 10 组，组内前瞻收益均值；Q1 = 因子值最小 |
| 多空价差 | Q10 − Q1 的平均前瞻收益（每个调仓周期） |
| 单调性 | 分位序号与分位收益的秩相关（±1 = 完美单调） |
| 换手率 | 十分位成员相对前一交易日的变动比例（单边，按当日有效样本归一） |
| 相关性 | 秩相关矩阵，逐日 `RᵀR` 累加后中心化；NaN 秩用该列**中位秩**填充 |
| 净值曲线 | 分位组合按 `前瞻 k 日收益 ÷ k` 折算到日均后复利（重叠期近似，图表内已标注） |

窗口默认**近 5 年**（`--years 5`），可选 `--start/--end/--step`；快照元数据里记录窗口与生成时间，
页面顶部原样展示 —— 避免「看的是哪个区间」说不清。

## 五、因子去重清单与 PDF 报告

相关性矩阵算好之后，「哪些因子是同一份信息」是可以直接产出的：

- **接口**：`GET /api/v1/factor-report/clusters?dataset=&threshold=0.9&keep=icir`
  —— 以 |ρ| ≥ 阈值建图取连通分量，每簇保留 |ICIR| 最大者为代表，其余标为重复项
  （返回每个成员「与代表的相关性」，间接相连的成员一眼可辨）。
- **页面**：因子报告页右上「因子去重」按钮 → 弹窗按阈值（0.8/0.9/0.95）浏览，
  可复制 Markdown；点任一因子直接跳到它的报告。
- **PDF 报告**：`python backend/scripts/factor_dedup_report.py`（`--dataset` / `--threshold` / `--keep`），
  产出 Markdown + 研报级 PDF 到**报告档案根**的 `因子去重/` 目录，
  技能中心「报告档案」可直接预览。
- **实测（2026-09-13，近 5 年窗口，|ρ|≥0.9）**：1071 个因子 → 147 个同源簇 → 建议剔除 341 个、保留 730 个；
  其中 Alpha 库 429 → 62 簇（126 个重复，最大簇 22 个成员）、L2 211 → 21 簇（64 个重复，
  最大簇是 `flow_*` 资金流家族 14 个成员）。

> ⚠️ **报告目录必须与档案读取同源**：报告档案根由 `trading_agents.py::_resolve_results_dir()`
> 解析（env `TRADING_AGENTS_RESULTS_DIR` → `/data/reports/trading_agents` →
> 旧目录 `/app/db/trading_agents_results`），**新目录不存在时会回退旧目录**。
> 曾有脚本写死新目录并把它建了出来，导致档案解析改指新目录、老报告在 UI 里"消失"（数据没丢）。
> `factor_dedup_report.py::archive_root()` 因此直接复用该解析函数——写报告的脚本都要这么做。

## 六、深度体检（六项）与多前瞻期

`backend/scripts/factor_deep_dive.py` 一次答完六个使用层面的问题（产出 Markdown + PDF，落「因子研究」目录）：

| 项 | 问题 | 数据来源 |
|---|---|---|
| A. IC 衰减 | 该多久调仓？ | 快照的 `ic_by_horizon`（T+1/2/5/10/20，一趟算完） |
| B. 中性化 IC | 有没有真 alpha（还是行业/市值暴露）？ | 行业（`instrument_detail.rs_hycode_sim` 128 类）去均值 + 市值（`valuation.total_mv`）正交后的残差 IC，抽样 step 天 |
| C. 扣费净收益 | 扣完手续费还剩多少？ | 序列的 q1/q10/换手 × 往返成本（默认 0.20%）= 净多空 + 盈亏平衡费率 |
| D. 拥挤度 | 是不是人多了？ | 滚动 250 日 IC 衰减 + 换手升高 + 多空回撤 >50% → 预警 |
| E. 组合构建 | 怎么配？ | 等权 / \|IC\| 加权 / 最大 ICIR（收缩 Σ⁻¹μ，含方向符号）；**组合 ICIR 用逐日 IC 序列合成**——不能用横截面秩相关矩阵（单位不同，会得出「分散化让 ICIR 变差」的假结论，实测修正后是提升 1.3~1.4×） |
| F. 可交易性 | 买得进吗？ | 涨跌停（分板块阈值 10/20/30%）+ 停牌（成交量 0）占比，抽样 step 天 |

**多前瞻期**：构建脚本 `--horizons` 默认一趟算全 5 期（秩与分位结构只算一次，各期只换 y），
写进快照的 `ic_by_horizon`/`ls_by_horizon` 与序列的 `ic_1..ic_20`/`ls_1..ls_20` 列。
页面指标条上有 **IC 衰减曲线**（峰值期用红点标出）——峰值在 T+20 = 慢因子（成本友好），T+1 = 快因子（成本敏感）。

### 7.3 ⚠️ 窗口一致性铁律（本次最重要的一条口径）

> **按天取均值的统计量一律走「请求窗口」；名字带 `_full` 后缀的累计序列一律走全窗口。**

理由：7 指标环、IC 均值、分组统计是**要一起读的一组数**；累计净值、累计 IC、
超额曲线是**曲线**，截断就失去意义。曾经在三个地方违反此规则，症状全是
「并排显示的两个数不同源，且都不报错」：

1. `headline_block` 收全窗口 `df` 却收窗口 `ic_all[cut]` → 同一行里 ICIR 描述 250 天、
   IR 描述 2588 天；250 天窗口的报告上显示十年累计收益。
2. `ic_block` 的 `ic_top_mean`/`ic_bot_mean`/`ic_neutral_mean`/`clip_frac_mean`/`n_valid_mean`
   用整列，而 `ic_mean`/`ic_std`/`win_rate` 用窗口 → `ic_neutral_days` 报 2564 配一张 250 点的图。
3. `excess_block` / `style_block` 的回归元与收益序列不同切 → 归因回归按下标对齐，日期错位。

4. `ic_block` 的 `cum_ic_top_full` / `cum_ic_bot_full` **名字带 `_full`、读的却是
   `df[tail_slice]`**（`top`/`bot` 是为均值统计准备的窗口切片，累计时误用了同一个变量）。
   同名的 `ic_cum_full` 用的是整列 `ic_all`、配 `cum_dates_full` —— 三条线画在**同一张图**上，
   两条半 IC 是 250 点、日期轴是 2600 个类目，ECharts 把它们放在最左侧 ~10%：
   **看着有图、其实只画了窗口那一段**。比少一张图更难发现。

已用 `test_factor_report_blocks.py::test_指标环与分组块描述的是同一个请求窗口`、
`::test_IC块里按天取均值的量全部走请求窗口`、
`::test_千日帧的响应体体积上限与两套轴各自成立` 三条测试锁住。第三条同时钉死
**每一条** `_full` 序列的轴长与体积上限（1.01 MB 实测 / 2 MB 上限），
两个断言职责不重叠：轴长抓「单条写反」，上限抓「成批膨胀」。

### 7.4 口径补充（接 §二）

| 指标 | 口径 |
|---|---|
| Returns | 多空组合年化 = 日均 × 252（**简单年化，不是 CAGR**，与 BRAIN 一致） |
| Fitness | `IR × √(\|Returns\| / max(Turnover, 0.125))`，0.125 地板是 BRAIN 约定（常量 `TURNOVER_FLOOR`） |
| Margin | `Returns / Turnover`（量纲不齐但是 BRAIN 既有约定，不改） |
| 多空组合 | G3 多 50% + G9 空 50%（可配），dollar-neutral，每日再平衡，`ls_t = 0.5 × (ret_G3 − ret_G9)` **毛收益** |
| 净口径 | 毛收益 − 双边成本 × 两腿换手均值；**换手缺失时整块置 `None`**，不退化等于毛收益 |
| 可交易双轨 | 理想轨（任何价位可成交）vs 可交易轨（剔除涨跌停/停牌/ST 后被挡的个股）。差额表达的是**理想口径高估了多少**，不是「策略会亏这么多」 |
| 容量 | 按当日全市场成交额中位数 × 参与率假设反推；**必须带假设值**，不给裸数字 |
| 纯因子收益 | 逐日 WLS：`r = Σ X_k f_k + Σ D_j d_j + ε`，权重 `√clip(float_mv)` |

**三个必须记住的坑**（都已在代码里注明）：

- `metrics.cum_curve` 返回 **净值因子 ∏(1+r)**（起点 `1+r₀`），**不是累计收益**；
  不减 1 会得到 0.99 这种数，前端按百分数渲染成「+99%」—— 量级看着合理，错 100 个百分点。
- 空头腿的累计要按 **∏(1−r) − 1** 重算（`short_cum` 是「做空标的持多头」的账）。
- `holding_period_sweep` 用的是 **Q10−Q1 极值价差**（parquet 现成的 `ls_1..ls_20`），
  不是可配的 G3/G9 —— 两者不可混读。

### 7.5 实测数字（2026-09-19 实测，**逐数据集分开记**）

⚠️ 各数据集的规模差一个量级，**引用时必须写清是哪一个** —— 「75 列」是共同点，
行数/体积/耗时都不是。下表全部为实测值，不是估算：

| 数据集 | `schema_version` | 天数 | `factor_series` 行 × 列 | 体积 | 构建耗时 |
|---|---|---|---|---|---|
| `alpha_library`（429 因子） | **2** | 1127（2022-01-04 → 2026-08-27） | 483,483 × **75** | **131 MB** | **574 s**（0.51 s/天） |
| `factor_defs`（1336 因子） | 1（待重跑） | 2588 | 1,110,252 × 75 | 278 MB | 1232 s（0.47 s/天） |
| `l1_factors` / `l2_factors` / `l1_l2_factors` | 1（待重跑） | 2354 / 1132 / 1132 | — | — | — |

- **列数 23 → 75**。新增：`ic_top`/`ic_bot`/`ic_neutral`/`ic_large·mid·small`/`clip_frac`/`n_valid`
  + `q1..q10_trad_long·short`（20）+ `gt1..gt10`（10）+ `blk_long_n`/`blk_short_n` + `sc_<style>`×10。
- **体积涨幅 2.67×**（factor_defs：104 → 278 MB）高于设计时的 1.6–1.8× 估计 ——
  实际列数远超方案里「+18 → 41 列」的算术：可交易轨的 20 列 `q*_trad_*` 与 10 列 `gt*`
  当时**没算进去**。方案里的列数表低估了，以实测为准。
- **耗时反而比估计乐观**（alpha_library +7%、factor_defs 与升级前持平）：半 IC / 分域 IC
  复用了**已算好的当日秩矩阵**，没有二次排序。
- 构建尾部会打印截面附加出数统计（`半 IC 429/429、中性化 429、分域 429/429/429、clip_frac 406`）
  —— 这是「零项即失败」闸门：某项若变成 0/N 而不是 N/N，说明该列没算出来，
  不能靠 available 掩过去。

| 旧快照（未重跑构建） | 「需重跑构建」（`meta.schema_version` 把关） |
| 风格产物缺失 | 风格页签降级提示，其余四个页签正常 |
| 可交易掩码不可用 | 可交易轨降级，理想轨照常 |
| 某指数取不到 | 该基准项置灰并说明；`bench_symbol` **自曝**实际用的是哪条，不冒充被点名的那个 |
| 盈亏平衡成本为负 | 显示 note 解释「倒收手续费才持平」并给出反向组合的值，不印成 -0.62bp 让人当 bug |
| 可交易轨含 ±inf | 曲线照算（坏日按 0 收益），并把 `invalid_days` 显式披露 |

`test_factor_report_blocks.py::test_可交易轨里的_inf_不再静默毁掉整条累计曲线` 锁住最后一条 ——
曾有一版构建洗了理想轨的 `inf` 却漏洗可交易轨，`inf` 进 `cumprod` 立刻溢出，
**整条累计曲线变 NaN 而 `available` 仍报 True**（判据是「有没有有限值」而非「有没有非有限值」）。

### 7.7 两类量各自带轴（2026-09-19 补）

§7.3 定的是「哪根轴用哪个窗口」；这一条定的是**同一个块里两类量并存时，前端拿哪根轴配哪条线**。
只写窗口口径不够 —— 块里必须同时给出两根轴：

| 块 | 日频型（服从 `lookback`） | 累计型（全窗口） |
|---|---|---|
| `ic_block` | `dates` / `ic_series` / `ic_rolling` / `ic_rolling_long` / `ic_neutral_series` / `ic_domain_series.*` / `ic_hist` / `ic_autocorr` | `cum_dates_full` / `ic_cum_full` / `cum_ic_top_full` / `cum_ic_bot_full` / `ir_rolling_full` |
| `group_block` | `dates` / `long_daily` / `short_daily` / `ls_daily` / `ls_dist` / `ls_monthly` | `cum_dates_full` / `long_cum` / `short_cum` / `short_book_cum` / `ls_cum` |
| `tradable` | `dates` / `ls_daily` | `cum_dates_full` / `ls_cum` |
| `excess_block` | `ls_dates` / `ls_daily` / `excess_hist` | `dates`（本块主体是累计型，故主轴即全窗口轴） |

**轴与序列不等长时前端整张图不画** —— 这是有意的：错位画出来只是横轴标签整体偏了，
图看着完全正常。宁可不画。

本次据此修掉四处**静默错**（症状全是「页面正常、数字不对」）：

1. **`excess_block` 整块按窗口切**，与它自己的 docstring「累计型」自相矛盾：
   250 天窗口下「分年度超额收益」只剩 2 根柱子（全样本 5 年 2022–2026），
   累计超额曲线从窗口起点重新起算。改法：主体接**全窗口**，`tail` 只截 `ls_daily` 这对日频输出。
   同一类错也在 `group_block` 的 `long_cum`/`short_cum`/`short_book_cum`/`ls_cum` 上 ——
   前端 ExcessTab 的「多头 vs 指数」曾因此**整张图不画**（全窗口 `ex.dates` 配窗口 `long_cum`，长度不等）。
2. **CSV 导出把两根轴当成一根用**：`ls_cum[i]` 与 `ls_daily[i]` 长度不同，同一行按同一个 `i` 取，
   后半段每一行的日收益都错位到别的日期上 —— 不报错，只是给出一张看着正常的表。
   改用累计轴出行、日频列按尾部偏移取，窗口外的日频格留 `—`。
3. **CSV 导出的 `long_excess_dd` 列恒为 `—`**：它读的是 `long_excess_dd`（**标量**，最大回撤那一个数），
   按 `i` 索引恒为 `undefined`，整列固定输出占位符。改成由 `long_excess_cum` 现算回撤曲线（与图表同一口径）。
4. **`cum_ic_top_full` / `cum_ic_bot_full` 名字带 `_full` 却按窗口切**（详见 §7.3 第 4 条）：
   与同图的 `ic_cum_full`（全窗口）共用一个 2600 类目的横轴，两条半 IC 只画在最左侧 ~10%。
   **这三条都是「名字/注释说 A、代码做 B」** —— 排查时先信名字、再去核代码，就会漏掉。

另有一处**发货前拦下**：`group_block` 重构后 `legs_turnover(df, ...)` 若仍用全窗口 `df`，
`turnover_ls` 会变成 1127 天均值，而 7 指标环的 Turnover 是 250 天均值 ——
同一张统计表上两个「换手」不同源。已改为先切 `dfw` 再算，实测断言
`group_block.turnover_ls == headline.turnover`（`0.5203223377466202`）。

### 7.8 拆文件与 façade 约定

两个超 800 行的文件（`blocks.py` 948、`metrics.py` 1257）拆成「实现分块 + 对外唯一入口」，
**对外名字一个不少** —— `import metrics as M` / `from . import blocks as BLK` 的调用方零改动：

- `metrics.py` → `metrics_core` / `metrics_eval` / `metrics_series`，依赖单向
  （`core ← eval`、`core ← series`，eval 与 series 互不依赖）。
- `blocks.py` → `blocks_common` / `blocks_ic` / `blocks_bench`，原文件留作入口。

拆完**必须证明没改行为**，两条缺一不可：

1. **导出名逐个对拍**：把 façade 的 `__all__` 与原模块 AST 取出的公开名做差集，必须为空
   （`metrics.py` 51/51，缺失 0）。
2. **端到端数字逐位相同**：实测 `headline.turnover = 0.5203223377466202`、
   `tradable.ideal_cum_end = -0.06975751720837697`、payload 0.485 MB，拆分前后完全一致；
   外加 244 条后端测试与 58 条探针断言全绿。

⚠️ **唯一例外**：`excess_block` 与 `bench_daily_returns` **必须留在同一模块**（见 §7.8 上文的替换接缝说明），
不能像其他函数那样按主题分家 —— 这条例外用测试里的一段注释钉住。

## 八、已知边界

- 相关性是**窗口内日均**口径（逐日秩相关矩阵的平均），不是「全样本一次秩相关」；
  两者在因子分布随时间的场景下会有差异，页面已标注「近 5 年日均」。
- 换手率是**十分位组合**的成员变动，不是因子值本身的换手；调仓成本建模仍需回测侧配合。
- 明细走预计算序列（~0.14s），但**序列与快照同生共死**：数据更新后要重跑脚本才更新；
  close_fwd 数据集（L1/L2/L1+L2）没有独立标签表，序列缺失时不提供慢速兜底（直接提示先构建）。
- L2/L1+L2 的分区从 2022 年起（1133 个），比 L1/alpha 的 2599 个短 —— 明细里 L2 系列的时间轴更短。
