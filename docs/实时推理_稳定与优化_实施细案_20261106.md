# 实时推理「稳定与优化」实施细案

> 版本：v1.0（2026-11-06）　承接：`docs/P6实时轨_实施细案.md` T-P6-08/09/10
> 定位：热集实时推理已在生产常驻（15s 节拍）。本文只做**稳定面修补 + 观测面补齐**，
> 不改发布口径、不切换模型输入；任何会改变分数分布的动作一律走影子（shadow），
> 拿到实测证据再谈切换。

---

## 一、背景与实测基线（2026-11-06 收盘后）

| 项 | 实测值 | 来源 |
|---|---|---|
| 模型 | `mdl_cust_train_20260917064612_33659b62_754461be`，nativetft，273 特征，20 日窗，T+5 | `metadata.json` |
| 热集 | 597 只（持仓 ∪ 实盘持仓 ∪ 候选池 ∪ 异动池，cap 2000） | `qm:hot_set:symbols` |
| 节拍 | 配置 15s；实际周期 = 15s 等待 + ~6.8s 计算 ≈ 22s | `qm:realtime:infer:status` |
| 本周期时延 | 6.8s（p95 7.2s） | governor |
| 当日发布 | 398/734 周期（其余 336 次为覆盖率闸门拦截；11:34–12:56 午休为主） | counters |
| 覆盖率 | 盘中 51–54%；15:23 跌破 50% 自动关闸（最后周期 87.8ms） | counters / last_skip |
| 盘中生效分数 | 639 只标的取实时行，2659 只仍取批量行 | `engine_signal_scores` 最新写入 |
| 覆盖白名单 | 2 列（`vol_gk_20, vol_std_10`）/ 增量引擎可算 32 列 | config / `feature_incremental.TIER_COLUMNS` |

**已确认的四个缺口**：

1. **心跳误报**：判活阈值 = 2×节拍 = 30s，但实际写入周期 ≈ 22s，且卡片 30s 才拉一次状态
   → 显示年龄必然周期性越过 30s，面板定期闪「心跳停更」，实际循环健康。
2. **覆盖率口径只证「喂数进程活着」**：`map_snapshot` 的 `timestamp = time.time()`（写入时刻），
   桥返回旧快照也会被算成「新鲜」；闸门无法区分「行情没到」与「桥在返回旧值」。
3. **热集覆盖天花板**：收盘后 Redis 仅 372 个 `market:snapshot:*` 键 / 热集 597
   → 覆盖率上限 62%，盘中实测 51–54%，离 50% 闸门仅几个点，行情源稍抖即整体停发。
4. **价值无法证明**：PG 每标的每日只留最后一行（upsert 覆盖），Redis 台账只存
   `scores_digest` 和均值、**不存每只票的分** → 无法回答「盘中分是否比批量分更有用」。

## 二、设计纪律

1. **不改发布口径**：A–E 不得改变 `engine_signal_scores` 的写入内容与频率；
   新增观测数据写独立表/键，失败只计数，不影响主循环。
2. **观测先于切换**：任何改变模型输入的尝试（扩展白名单）只做 shadow，
   结果单独落盘，生产分数保持现状。
3. **单项可回滚**：每项都有独立开关或独立读路径；关掉即回到今天的行为。
4. **不新增重启面**：A 是前端构建期改动；B–E 后端改动按 OSS 热加载杀对应子进程，
   不 `docker restart`。

## 三、任务清单

### T-RT-01 心跳判活口径修复（前端，零风险）

**问题**：`HEARTBEAT_STALE_FACTOR * cadence` 与实际「等待 + 计算 + 轮询延迟」不符。

**做法**：
- 判活阈值改为 `2 × (节拍 + 本周期耗时) + 轮询间隔`，本周期耗时取
  `counters.last_ms / 1000`（上限 = 节拍，防一次异常长周期把阈值撑爆）；
- 卡片轮询 30s → 10s（只读 Redis 镜像，开销可忽略）；
- 文案带上「节拍 15s + 本周期 7s」，让运维一眼看出阈值怎么来的。

**验收**：正常运行时任意两次轮询之间的显示年龄 < 阈值；构造「镜像 60s 未更新」用例仍判 stale。

**回滚**：前端回退构建产物。

---

### T-RT-02 行情前进校验（后端，旁路观测）

**问题**：覆盖率只看写入时刻，桥返回冻结快照时闸门不响。

**做法**：
- 服务内按标的记录上一轮 `(Volume, Amount, Now)`；本轮与上轮相同 → `frozen`，否则 `advanced`；
- 每周期计数：`quote_compared / quote_advanced / quote_frozen / last_advance_ratio`；
- **只计数不拦截**（是否纳入闸门待观测两周后另议）；
- 同时统计热集「从未见过快照」的标的数（服务启动/日切后累计），回答「从未写入 vs 写过又过期」。

**验收**：收盘后（行情冻结）`advance_ratio` 显著下降并如实上报；盘中正常时 > 0；
采集失败不影响主循环。

**回滚**：删计数即可，无行为影响。

---

### T-RT-03 热集覆盖诊断（后端脚本 + 计数）

**问题**：597 只里 225 只在 Redis 无快照键，原因未知（桥不支持指数？轮转一圈超过 300s TTL？映射失败？）。

**做法**：
- 脚本 `backend/scripts/realtime_coverage_probe.py`：读热集 + `market:snapshot:*`（含 TTL），
  按 `fresh / stale / expired / missing` 分档，输出按代码段（SH6/SZ0/SZ3/指数）的汇总，
  支持 `--json` 供定时采集；
- 服务侧计数 `hot_symbols / snapshot_symbols / never_seen`（见 T-RT-02）。

**验收**：盘中每 10 分钟采样一次，连续两个交易日，能区分「从未写入」与「写过又过期」；
指数（000001.SH / 000300.SH）单独列出。

**回滚**：纯脚本，无副作用。

---

### T-RT-04 扩展白名单影子（后端，不改生产）

**问题**：273 特征只有 2 列盘中更新；增量引擎可算 32 列，但「盘中半日 bar」与「收盘值」
分布不同，直接扩白名单有口径漂移风险。

**做法**：
- 配置新增 `shadow_whitelist`（默认空 = 关闭）与 `shadow_every_n_cycles`（默认 20）；
- 每 N 个周期，用**同一份快照/基线/窗口**再跑一次 `compute_cycle`（`feed_engine=False`，
  不重复喂引擎状态），仅替换覆盖列集合；
- 比较生产分与影子分：秩相关（Spearman）、平均绝对差、Top20 重合数；
- 结果写 Redis：`qm:realtime:infer:shadow:last`（hash）+ 日账本列表（上限 4000 条，TTL 7 天），
  并在状态镜像 `shadow` 段暴露给面板；
- **不发布、不写 `engine_signal_scores`**；影子异常只计数，不影响主周期；
- **白名单无可扩列时直接跳过**（`shadow_override == 生产 override` → `shadow_noop` 计数）：
  再算一遍必然得到相关系数 1.0，白烧算力；
- **过载降载时让路**（`degraded_level ≥ 1` → `shadow_skipped_degraded`）：影子是纯可选
  重算，不许和保命降载抢算力。

**2026-11-06 实测前提（重要）**：当前生产模型 273 个特征是 `JQ110_*` 命名，与 `TIER_COLUMNS`
32 列的交集**只有 2 列**（`vol_gk_20, vol_std_10`）——**正是已启用的两列**。也就是说
这个模型没有"再扩几列"的空间；影子机制是为后续「特征名与 TIER 同源」的模型准备的。
想让盘中信号有更多实时输入，只有两条路：① 训练一个用 TIER 同名列的模型；② 为
JQ110 特征做实时近似计算（当前不存在）。**不要**为了"把白名单填满"而启用影子——
交集不变，只会得到 1.0。

**判据（kill criteria）**：若影子秩相关 < 0.9 或 Top20 重合 < 15/20，说明半日 bar 口径
已实质改变排序，**不进入下一步**，先查特征分布。

**验收**：开启后主周期时延增量 < 0.5s；影子结果连续 5 个交易日可查；主分数零变化。

**回滚**：`shadow_whitelist` 置空即停。

### T-RT-05 盘中分数时序采样（后端，新增表）

**问题**：没有盘中分数历史，无法评估「盘中分 vs 批量分」的预测力。

**做法**：
- 新表 `engine_realtime_score_samples`（`CREATE TABLE IF NOT EXISTS` 自愈，不写迁移）：
  `run_id / trade_date / sample_ts / symbol / model_version / feature_version /
   variant / score / score_rank / rank_pct / live_coverage / degraded_level / created_at`，
  唯一键 `(sample_ts, symbol, model_version, variant)`，冲突 `DO NOTHING`；
- 服务每 `sample_interval_s`（默认 300s，0 = 关闭）在**发布成功后**批量写一次，
  每轮 597 行、单条多行 INSERT；
- 影子分（T-RT-04）同表 `variant='shadow'`，与生产分同刻可比；
- 保留期 `QM_REALTIME_SAMPLE_KEEP_DAYS`（默认 180 天），每天最多清理一次。

**验收**：单次写入 < 300ms；同 `sample_ts` 重放幂等；按 `trade_date + variant` 能直接算
IC / 分组收益；主链路异常时采样失败只计数（`sample_errors`）。

**回滚**：`sample_interval_s=0` 即停写；表可保留不影响任何读路径。

## 四、顺序与验证

1. T-RT-01（前端）→ `npm run typecheck` + vitest → `scripts/deploy_frontend.sh`
2. T-RT-02/03（后端观测）→ 单测 + 引擎子进程热加载 → 次日盘中看计数
3. T-RT-04（影子）→ 先空跑 1 天确认零影响，再配 32 列全量影子
4. T-RT-05（采样）→ 建表幂等验证 → 观察 2 个交易日写入量与耗时
5. T-RT-06 待数据齐后另立细案

**验证纪律**：每项都要有失败用例（采集失败、影子异常、重复写入）；不得以
「日志看起来正常」代替断言；改动后按 OSS 热加载杀对应子进程，判据 = 端口持有者换人。

## 五、风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 影子计算拖慢主周期 | 发布延迟 | 每 N 周期一次 + 主周期耗时增量 < 0.5s 验收线，超线自动跳过影子 |
| 采样表增长 | 磁盘 | 180 天保留 + 每日清理一次；597×~80/日 ≈ 4.8 万行/日 |
| 观测计数字段膨胀 | 面板/镜像体积 | 只加标量计数，不加逐标的明细到镜像 |
| 配置误写 | 影子列不在模型特征内 | 管理端点沿用「白名单 ⊆ feature_columns」校验 |
