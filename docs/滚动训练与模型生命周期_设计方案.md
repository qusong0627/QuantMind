## 零、TL;DR

| 问题 | 结论 |
|---|---|
| 滚动训练怎么实现 | 不新造训练系统：**窗口计算器（纯函数）+ 月度调度器（复用 market_sync 派发模式）+ campaign 记账**，把"人肉每月改日期重训"变成"Redis 配置一处开关"。派发必须绕开 celery worker（无 docker.sock），走内部 HTTP 进 API 进程的既有训练提交入口。 |
| 模型时好时坏怎么治 | **先归因后治疗**：regime 时间线落库 → 分桶 IC → 告警带归因 → （可配）降险建议；换模型是最后手段且永远人工确认。不做按 regime 训练独立模型。 |
| 晋升怎么保证不翻车 | 三层证据（训练内 by_split → vintage 回放配对检验 → 20 交易日**观察期**前向 IC），过闸门 + 人工点头才切默认；随时可回滚到上一任且有审计。 |
| 前置硬修复 | 5 项 P0（`/compare` 键错、质量回填收益源、僵尸作业、训练单飞锁、by_split 口径固化）——不修这些，滚动训练建在坏地基上。 |
| 命名冲突 | 执行侧已有 `shared/shadow_compare.py`（模拟单 vs 真单，T-P2-06）。**模型侧一律叫「观察期（observation）」**，不叫影子，避免两套"影子"混线。 |

分期：**P0 修复（1-2 周）→ P1 滚动训练 MVP（2-3 周）→ P2 评估与晋升（3-4 周）→ P3 regime 感知（2-3 周）→ P4 组合与治理收尾（按需）**。每期独立可用、默认关闭新入口。

## 一、问题定义与设计原则

### 1.1 两个问题，一句话版本

- **问题 A（工程）**：平台只有"手动单窗训练"——用户自己填 train/valid/test 日期、自己盯完成、自己切默认。没有周期性重训链路：无调度、无队列、无版本记账、无晋升闸门、无回滚。
- **问题 B（科学）**：模型 IC 随市场状态系统性起伏。实测结论（`nativetft-training-recipe` / `model-ic-is-size-regime-bet`）：月间 IC 与「小减大」风格价差相关性 +0.62~+0.73——**大部分"模型变差了"其实是风格逆风，不是模型坏了**。当前平台没有任何环节把这两者区分开：IC 告警不认 regime、评分卡没有 regime 维度、`engine_signal_scores.regime` 列硬编码 `'normal'`（`script_runner.py:2508`，实测）。

### 1.2 设计原则（违反即打回）

1. **复用优先**：窗口用既有 `split.{train,valid,test}` 契约（`docker/training/data/splits.py` 已支持显式三段+尾部 embargo）；调度抄 `market_sync_scheduler` 的派发纪律；评估挂既有评估中心 `backend/scripts/eval/`；IC 台账用既有 `qm_model_inference_quality`（本就是 (model_id, trade_date) 多模型键）；regime 用既有单源 `backend/shared/market_regime.py`。**新增面尽量薄**。
2. **先诊断后治疗**："模型不好"先做 regime/风格归因，够不上"模型损坏"证据链的不换模型。
3. **先观察后生效**（ADR-0009 的模型版）：challenger 先跑观察期前向 IC，**绝不允许写进生产信号的读路径**。
4. **换模型是人工决策**（默认）：闸门只产出"建议晋升"的证据卡；自动晋升是 P2 验收后才可开启的配置项。
5. **每期独立可用**：P0 修复本身就是收益；P1 不依赖 P2，P3 不依赖 P4。
6. **不许静默**：新载荷键必须进白名单（教训：`feature_selection` 旧键名被白名单静默丢弃，`training-payload-feature-selection-default`）；调度派发失败不写 last_run；降级动作必须有告警与审计。

## 三、总体设计

### 3.1 模型生命周期状态机

**不改** `qm_user_models.status` 既有语义（candidate/syncing/ready/active/archived/failed——前端与既有链路依赖它）。在其上叠加 **rollout 层**（新表 `qm_model_rollouts`）：

```
                        ┌────────────────────────────────────────────────┐
 训练完成 ──注册──▶ candidate ──软闸门──▶ ready ════════════╗
                        │                                   ║
              （进入晋升流程，创建 rollout）                    ║  既有语义域
                        ▼                                   ║
   registered → replay_eval（vintage 回放配对）               ║
                        │ 过 G0-G4                                ║
                        ▼                                   ║
   observing（观察期 ≥20 交易日，前向 IC）                     ║
                        │ 过 G5-G6                                ║
                        ▼                                   ║
   gate_passed ──人工批准──▶ promoted ═══▶ set_default(challenger)
                        │                    （champion 降为备任）  ║
                        ├── reject ──▶ rejected（关 settings 行）    ║
                        └── 事后异常 ──▶ rolled_back ══▶ set_default(prior_default)
                                                          ╚══════════╝
```

- rollout 的每一跳都写审计（谁、何时、证据 JSONB、理由）。
- **champion = 当前 is_default（该市场）**；备任链 = `prior_default_model_id` + rollout 历史。
- 观察期结束未晋升 → 默认自动关掉其 settings 行（防观察残渣常驻推理名单）。

### 3.2 端到端数据流

```
QuantDB（唯一数据源，ADR-0007）
   │
   ├─▶ 重训调度器（新，celery beat 每分钟）
   │      │  Redis 配置 quantmind:retrain_schedule:{market}（默认全关）
   │      │  due？→ busy？（单飞锁+活动作业）→ 数据就绪？（label max_date）
   │      ▼ 内部 HTTP POST /api/v1/internal/rolling/dispatch（X-Internal-Call-Secret）
   │   窗口计算器（纯函数，交易日历）→ split 三段 + purge 间隔 + rolling_meta
   │      ▼ 既有 submit_training_job
   │   训练容器（既有编排；campaign 记账 qm_rolling_campaigns）
   │      ▼ 训练完成回调 → 既有注册（candidate → 软闸门）
   │
   ├─▶ rollout 服务（新）：
   │      replay_eval：vintage 回放拼接 OOS + 配对检验（vs champion，同日期同池）
   │      observing：开挑战者 settings 行 → 既有日更管线跑 → 既有质量回填算 IC

   └─▶ 常态监控：qm_model_inference_quality（已有）→ eval_scores/序列（已有）

## 四、滚动训练（工程实现）

### 4.1 窗口口径（walk-forward）

**默认 WindowPolicy（CN，月度）**——全部按**交易日历**计算，禁止自然日近似：

| 段 | 默认 | 说明 |
|---|---|---|
| test | anchor 往前 63 交易日（≈3 个月） | 只做一次，出闸门证据，不进任何调参 |
| purge₁ | test 起点前 `horizon+1` 交易日 | 消除 train/valid 标签窗与 test 特征窗的重叠 |
| valid | test 前 126 交易日（≈6 个月） | 早停/选择 |
| purge₂ | valid 起点前 `horizon+1` | 同上 |
| train | valid 前 756 交易日（≈3 年，sliding；可选 expanding） | 覆盖一轮牛熊+风格切换 |
| anchor | `min(因子 max_date, 标签 max_date − horizon)` | 数据滞后守卫：不满足则整窗回退一位 |

- **purge 实现方式（先薄后厚）**：P1 由窗口计算器在边界间**留出间隔**（`splits.py` 既有尾部裁 `horizon+1` 兜底）；P2 回放评估换用 `skills/ml-purged-cv` 的区间重叠口径（`CausalWalkForward`），并给 `_generate_oof_predictions` 补上缺失的双侧 purge（`train.py:821` 现状单侧）。
- **载荷形态**：dispatcher 直接把窗口物化为既有显式 `split`（`splits.py` 显式路径优先，不走 val_ratio 回退）→ **train.py 切分逻辑零改动**。
- 每次重训 step=1 个月；`wfa` 诊断对树/线性配方默认开（轻量），DL 配方自动跳过（`wfa.py` 本就不支持 DL）。

### 4.2 调度与派发

  "recipe_id": "cn_nativetft_base", "window_policy": {"train_days": 756, "valid_days": 126,
  "test_days": 63, "mode": "sliding"}, "purge_days": null, "observation_days": 20,
  "max_time_minutes": 240, "executor": "local", "last_run": null }

- 未配置 = `enabled:false`（与 `market_sync` 同一默认哲学：不内置默认调度）。

        "滚动训练：窗口计算→内部派发→campaign 记账；mark-after-dispatch")
```

- **派发链路**（硬约束驱动）：celery worker **无 docker.sock**（compose 实测），训练容器只能由 API 进程的编排器启动 → beat 任务只做"到点判定 + HTTP POST 内部端点"，真正的提交发生在 API 进程：

```
beat(retrain_scheduler.tick)
  → 读 Redis 配置；due？（日规则 ∩ 交易日历 ∩ last_run 非本 due 期）
  → busy？ 单飞锁持有 ∨ admin_training_jobs 有活动行 → 本次不派发（不写 last_run，下一 tick 重试）
  → 数据就绪？（anchor 计算，滞后则跳过 + 当日一次告警）
  → POST http://127.0.0.1:8000/api/v1/internal/rolling/dispatch
       body: {market, recipe_id, window_plan?, dry_run?}   header: X-Internal-Call-Secret
  → 2xx 才写 last_run + 心跳 qm:sched:hb:retrain_dispatch
```

- **内部端点**（`/api/v1/internal/rolling/dispatch`，密钥治理同 ADR-0011）：计算窗口 → 落 `qm_rolling_campaigns`（status=planned）→ 组 payload（recipe + 显式 split + `wfa` 诊断 + `rolling_meta`）→ 调既有 `submit_training_job` → 回填 run_id。**不新增第二套训练提交路径**。
- 手动入口：既有「模型训练」页与外部门面 `POST /task kind=training` 不动；新增 CLI `python backend/scripts/rolling_train.py --market CN [--dry-run]`（P1 演练用，dry-run 只打印窗口与载荷）。

### 4.3 串行与资源（血泪纪律固化为代码）

1. **单飞锁**（P0-3 落地）：`qm:training:singleflight`（SET NX EX，TTL = max_time_minutes×60 + 600，持有者按 run_id 续租）。取锁点在**共享提交入口**（`admin_training_utils.submit_training_job`），UI/外部门面/调度器/批跑器一视同仁；占用中再提交 → 409「训练进行中（run_id=…）」。批跑器等 2xx 语义不变。
2. **内存守卫**：派发前读宿主 `MemAvailable`，低于阈值（默认 50G）跳过本 tick 并告警一次/日。理由：真上限是主机可用内存 ~44G，不是容器 cgroup（`training-memory-budget` 实测）。
3. **探针禁令**：任何 40G 级探针/回放任务不得与训练并发——回放 vintage 走夜间串行或远程节点（`executor: "remote"`，AutoDL 链路已就绪）。
4. **超时**：沿用既有 timeout kill（`local_docker_orchestrator.py` max_time_minutes）；滚动配方默认 240min（DL 全链实测 2h31m）。

### 4.4 故障自愈（把 `recover_pending_runs` 接上线，但拆成两步）

**判尸与重投分离**——重启后直接重投会在"旧容器其实还活着"时双跑，必须两步走：

1. **`reconcile_training_jobs()`（P0-3，启动期 + 每小时 beat）**：对非终态作业判尸——
   - Docker：容器 `qm-train-{run_id}` 不存在；
   - Process：PID 不存活；
   - Remote：SSH 会话不可达 ∨ 心跳超时；
   - 或超过 `1.5×max_time_minutes`。
   判死 → 标 `failed(reason="orphaned_after_restart")` + **释放单飞锁** + 告警。**默认不自动重投**（比现状前进一大步：不再有永挂 running）。
2. **滚动场景的重投（P1，可选开）**：campaign 行提供幂等锚——同 `(campaign_id, window_index)` 已有 completed/registered → 不重投；仅 failed → 最多重投 1 次，仍失败 → campaign 标 failed + 告警。

### 4.5 快照与可复现

- **`recipe_hash`**：payload 规范化 JSON（sorted keys）的 sha1，落 campaign。同 recipe 的所有 window 可对账；重训的"配方漂移"（偷偷改了特征/参数）在数据上可见。
- **`data_fingerprint`（写进 metadata.json）**：`factor_source` / `catalog_version` / `schema_hash`（训练器已有）+ 本次实际 train/valid/test 区间与行数 + `prices_max_date` / `labels_max_date` + QuantDB 分区 manifest 摘要（文件数+mtime 摘要）+ `computed_at`。
- **可复现三件套**：seed（train.py 固定 42）+ config.yaml（job 目录已存）+ data_fingerprint。缺任何一件的 run 不允许进晋升流程（G0 扩展检查）。
- 配套纪律（来自 `ml-purged-cv-skill` 实测）：**标签一律自 `daily_forward` 重算**（`features_daily` 标签列 20260828 后停填；`daily_backward` 是坏复权序列）。

### 4.6 触发式重训（三条触发源，同一出口）

| 触发源 | 判定 | 动作 |
|---|---|---|
| 定时（主） | Redis 配置 due | 建 campaign → 派发（本方案 §4.2） |
| IC 异常 | sentinel 模型 IC 告警持续 N 交易日（默认 5） | 建 campaign（`trigger=sentinel`）→ **仍只产 candidate**，不替换 |
| 数据漂移 | PSI/因子漂移序列超阈（既有 drift 产物） | 同上（`trigger=drift`） |

所有触发共用 campaign 出口与闸门——**没有任何路径可以直接改 is_default**。

### 4.7 载荷契约扩展（白名单陷阱，必须照做）

payload 新增 `rolling_meta`：

```json
{ "campaign_id": "...", "window_index": 3, "anchor_date": "2026-09-30",
  "recipe_hash": "...", "purge_days": 2, "dispatched_by": "retrain_dispatch" }
```

落地清单（少一步就静默丢，先例 `feature_selection`）：
1. `backend/shared/training/per_model.py` 的 `_SHARED_FIELDS` 加 `rolling_meta`；
2. `admin_training_utils` 归一化白名单同步；
3. `backend/shared/training/schemas.py` `TrainingConfig` 加可选字段（+ `CONDITIONAL_KEYS` 视契约导出而定）；
4. `docker/training/train.py` 读入并写入 `metadata.json`；
5. 单测：载荷往返 `rolling_meta` 存活断言（防回归）。

### 4.8 交付物与验收（P1）

- 交付：窗口计算器（golden）+ 调度器（mark-after-dispatch）+ 内部端点 + campaign 表 + fingerprint + CLI。
- 验收：① 一次真实 CN 月度重训**全自动**走通（配置→派发→训练→注册 candidate→campaign=registered）；② busy 时正确跳过且下一 tick 补发；③ 训练中 `kill -9` API → 重启后作业被标 `orphaned`，无永挂 running；④ `rolling_train.py --dry-run` 窗口输出与 fixture golden 一致。

## 五、样本外评估与晋升（champion / challenger）

### 5.1 三层证据

| 层 | 口径 | 数据源 | 用途 |
|---|---|---|---|
| L1 训练内 | `by_split.test`：mean IC + t + 天数 | `result.json`/metadata（既有） | G0 准入（沿用软闸门）；**headline 仅作训练收敛内部信号，不参与任何决策**（实测虚高 1.47×） |
| L2 vintage 回放 | 同 recipe 历史窗口拼接 OOS + **与 champion 共同日期配对检验** | `walkforward_rollup.py`：campaign → 各 run `pred.parquet` 的 test 段；champion 同窗 pred | G2/G3/G4/G6 |
| L3 观察期（前向） | ≥20 交易日 live IC/coverage | 既有日更管线 + `qm_model_inference_quality` | G5；也是最终"真环境"证据 |

- **L2 补跑**：初期无历史 vintage 时，先补 6-12 个历史锚点（`rolling_train.py --backfill --anchors ...`），夜间串行/远程节点，**不在关键路径**；补跑完成的 campaign 同样是 G2 证据源。
- **配对检验口径**：ΔIC = challenger_daily_ic − champion_daily_ic（共同日期 ∩ 共同池），单侧 t 检验；池不同先取交集（教训：跨池比均值必先取共同池）。
- **排名/对比前置（进 G1）**：先查产物独立性——指标逐位相同 + pred md5 相同 = 复制品，直接拒绝进入对比（HK 13 子模型复制事件）。

### 5.2 晋升闸门（G0-G6，全部可配；默认"观察模式"=只算不自动动作）

| 闸 | 条件（默认建议值） | 证据源 | 不过的后果 |
|---|---|---|---|
| G0 准入 | 注册软闸门已过 ∨ 已有 ready | 注册表（既有） | 不进流程 |
| G1 独立性 | 指标不逐位相同 ∧ pred md5 不同 ∧ 可复现三件套齐 | L1 + 产物 | 拒绝 |
| G2 回放非劣 | mean ΔIC ≥ −0.002 且 t(Δ) ≥ −1.0（非劣）；或 mean ΔIC > 0 且 t ≥ 1.5（优效） | L2 | 拒绝 |
| G3 稳定性 | 近 12 个月：最差月 ≥ champion 最差月 − 0.02；月间 std ≤ 1.5×std(champion) | L2 | 拒绝 |
| G4 状态依赖 | 无"champion 达标而 challenger 崩坏"的 regime 桶（桶内 ≥15 天、challenger ≤0 且 champion >0.01） | L2 + regime（P3 后为硬数据，之前跳过并标"未评估"） | 拒绝或人工裁决 |
| G5 观察期 | ≥20 交易日：mean rank_ic ≥ max(0.005, 0.9×champion 同期)，coverage ≥ 0.9×champion | L3 | 拒绝（可延长观察一次） |
| G6 成本 | 估算年化换手 ≤ 1.3×champion | realized_stats/turnover（既有） | 拒绝或人工裁决 |
| G7 提示 | 同 recipe 试次计数展示（防 p-hacking 决策偏差） | campaign/rollout 计数 | 仅展示 |

- 目标函数统一为 **mean rank IC（+t）**，不用 ICIR（分母是家族常数，跨家族不可比，实测 GBDT≈0.15 / DL≈0.11-0.13）。
- 阈值先给"观察模式"（PASS/FAIL 展示但不拦），积累 3-5 次真实决策后 P2 末评审是否开硬闸。

### 5.3 观察期（Observation）——不写生产读路径

**前置硬修复（P2-0，先做）**：信号读路径按模型桶过滤。

- 现状：`engine_signal_scores` 写侧已按桶隔离（`feature_version=script_v1_{model_id}`，冲突键含桶），但读侧（`backend/shared/signal_scores.py:44-65`、`backend/services/engine/scanners/model_signal_loader.py:29-105`）不过滤 → **任何候选模型的批量推理都会混进生产读取**（现存真实污染源）。
- 修法：新增唯一的**生效模型解析 → 桶解析**助手（复用 `resolve_effective_model_sync` 的优先级；桶计算复用 `script_runner._resolve_feature_version`，上收为 shared 函数）。所有默认读取 = 只读生效模型桶；解析不到生效模型 → 不猜（显式告警 + 空结果，而不是全桶混读）。多模型管理视图走显式参数。
- 测试：双桶夹具（生产桶+候选桶），断言默认读取只见生产桶；回归比对存量单模型用户读数逐位一致。
- 风险与回退：这是行为变更，需在上线前跑一周影子读比对（新旧结果 diff=0 才切默认）；有风险时回退开关。

**观察期运行（前置修好后）**：

1. rollout 服务把 challenger 行写入 `qm_model_inference_settings`（`enabled=TRUE`，`services/model_inference_persistence.py`）→ **既有日更管线**自动跑它（同桶隔离，写侧本就正确）；
2. 既有质量回填（补 market 参数后）算 challenger 日 IC → `qm_model_inference_quality`（多模型表，天然共存）；
3. 满 20 交易日 → G5；晋升则保留 settings 行并 set_default；拒绝/超时则关行。
4. 成本控制：树/线性 challenger 日更成本 ~分钟级；DL challenger 观察期默认降频（每周 1 次、`observation_days` 按次数折算）或仅在本地低峰。
5. **Plan B**（若读路径修复评审不通过）：观察期改走独立小表 `engine_observation_scores`（同 schema 子集，完全绕开生产表）。默认走 Plan A（复用），B 仅作备胎。

### 5.4 晋升 / 回滚 / 审计

- 表 `qm_model_rollouts`：`rollout_id / tenant_id / user_id / market / campaign_id? / champion_model_id / challenger_model_id / stage / gate_result JSONB / evidence JSONB / prior_default_model_id / decided_by / decided_at / created_at / updated_at / notes`。
- **晋升**（事务）：`set_default(challenger)` + 记录 `prior_default_model_id` + stage=promoted + 审计。
- **回滚**：`set_default(prior_default_model_id)` + stage=rolled_back + 审计（理由必填）。**修既有缺陷**：`archive` 归档 default 时现行回退"最近更新的 ready"——改为优先回退 `prior_default/上一任 champion`（rollout 表可查），查无才退回"最近更新"。
- **审批**：默认人工（机构四眼原则；OSS 单用户版降级为"双确认弹窗+理由输入"）。自动晋升仅当 rollout 配置显式 `auto_promote=true` 且连续 N=3 次闸门结论与人工决策一致后，才允许评估开启（P4 议题）。
- 前端治理页（P2）：每市场 roster、champion 旗帜、challenger 观察进度（n/20）、G0-G6 证据卡（复用修好的 `/compare`）、晋升/拒绝/回滚按钮（二次确认+理由）。类型检查 + `bash scripts/deploy_frontend.sh`（仓库纪律）。

### 5.5 多市场冠军（独立可推进的结构修复）

现状：`uq_qm_user_models_default_per_user` ON `(tenant_id, user_id) WHERE is_default` → 一个用户全局仅一个默认，CN/HK 模型互相顶掉（实测 DDL:165-167）。market 在 `metadata_json->>'market'`（`:575`）。

- 迁移：`DROP INDEX uq_qm_user_models_default_per_user` → `CREATE UNIQUE INDEX ... ON qm_user_models (tenant_id, user_id, COALESCE(metadata_json->>'market','CN')) WHERE is_default = TRUE`。**（2026-10-09 升级）**：口径改为 `qm_market_of(metadata_json)`——裸值 COALESCE 会漏未知/别名市场值（如 'CUSTOM'，验收③演练实测），见 `data/upgrade_v1.1.4.sql` 与 P2 落地记录。
- 存量审计：现库多市场模型共存时只有一个 is_default，迁移前先 dry-run 列出"每市场 updated_at 最新 ready 模型"作为该市场 default 的保留集，人工确认后 apply，**写后回读**（存量修复工具四条纪律）。
- SQL 走 `data/upgrade_*.sql` 系列——注意 `data/` 是符号链接且 `git add -A` 有真删先例，**逐文件 add**。

## 六、Regime 感知层（"有时好有时坏"的正解）

### 6.1 口径统一（唯一单源）

- **canonical = `backend/shared/market_regime.py`**：三态 `bull / neutral / bear`，阈值唯一（`DEFAULT_THRESHOLDS`），`build_state_series` 无前视（t 日状态 t+1 生效）。
- 词表收编清单：`factor` 报告自有 regime（离线展示，标注口径名，不并入）｜`fusion_config.regime_weights`（**死代码，P4 删除**，复活的唯一门票是 §6.5-L3 的 OOS 回放验收）｜`engine_signal_scores.regime` 硬编码 `'normal'`（P3 处置，见 6.4）。
- 各市场指数映射：CN=000300.SH（既有默认）；HK/US 用各自指数（HSI/SPX，数据可得性 P3 实测）。**取不到就缺行，不许拿 000300 冒充**（诚实拦截）。

### 6.2 时间线持久化

- 表 `qm_regime_daily(market, trade_date, state, ret_window, vol_window, volume_ratio, thresholds_hash, computed_at, PK(market, trade_date))`。
- 日更：beat `regime_daily_persist`（交易日 16:30；JobSpec `regime_persist`，`REGIME_PERSIST_ENABLED` 默认 on——纯计算小表，风险低）；回填 CLI `backend/scripts/regime_backfill.py --market CN --from 2018-01-01`。
- **写入按"生效日"**（沿用 `build_state_series` 的 i→i+1 口径）；历史行一经写入不得事后重算覆盖（`computed_at` 留痕）；golden 测试扩展既有 `test_market_regime.py`。

### 6.3 分桶评估（评估中心）

- eval 层对每个模型：daily IC 序列 join `qm_regime_daily`（按**信号日**）→ 各桶 mean IC / 命中率 / 天数 → 落 eval_series sidecar + 模型卡新增「状态依赖」区块。
- 展示口径（强制）：弱区标注 + **最差月与月间 std 优先**；禁止用年均 IC 单值对外（记忆：模型 IC 是市值风格的下注）。
- `qm_model_inference_quality` 不加速度列——分桶在 eval 层 join 算（保持质量表语义=逐日生产台账）。

### 6.4 告警归因（用 regime 降误报，不用 regime 掩盖真断链）

在 `detect_model_anomaly`（`anomaly_detectors.py:318`）发报前插入归因（纯函数 `attribute_ic_anomaly`）：

```
若 当前 regime ∈ 模型历史弱区（桶 IC ≤ 0 且桶内 ≥15 天）
   且 当期 IC 落在弱区历史分布 2σ 内
→ 降级 info + 标注「regime 归因（弱区，在期望内）」+ 附弱区统计
否则 → 照常告警（severity 不变）
```

- 必要条件：当日 regime 可得（前一日 16:30 已落库，08:00 推理可用——无前视）。
- 建议开启生产 IC 告警（`qm:engine:anomaly:config` 当前默认 false）：先观察两周，阈值建议"ic_5 滚动 20 日均 <0 且持续 5 交易日"（与 f8dd6dca 的 12h 冷却不冲突）。
- `engine_signal_scores.regime` 列：P3 先 grep 清点消费方；无消费方 → 推理时填当日 `qm_regime_daily` 生效值（比 `'normal'` 撒谎好）；有按 `'normal'` 分支的消费方 → 先改消费方再填。

### 6.5 动作阶梯（每级独立配置，默认全关，按序开启）

| 级 | 动作 | 默认 | 依赖 |
|---|---|---|---|
| L0 | 展示：模型卡/推理中心 regime 分桶 | 开 | 6.2/6.3 |
| L1 | 告警归因（§6.4） | 开 | 6.2 |
| L2 | 降险建议：弱区判定 → `POSITION_BY_STATE`（1.0/0.7/0.3，已有链路）下调建议 | 关 | L1 + 人工确认 |
| L3 | 组合权重：多模型融合按 regime 切权重 | 关 | **必须过 OOS 回放验收**，否则不复活死代码 |

### 6.6 明确不做（写进方案防止后来人跑偏）

- **不做 per-regime 独立训练**：样本割裂、标签跨窗、每个桶的过拟合风险远大于收益；regime 是"认识与降险"维度，不是"多训几个模型"的借口。
- **不做 regime 预测择时**：我们只识别当期状态，不预测切换时点；任何"预测下月 regime 再换模型"的提案先过 OOS 证据门槛。
- **不做 regime 事后重算覆盖**：时间线一经落库即冻结（审计要求）。
